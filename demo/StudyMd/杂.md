#### CSRF 【CrossSite RequestForgery】跨站请求伪造
攻击者引诱受害者进入第三方网站，在第三方网站中，像被攻击网站发送跨站请求。由于在被攻击网站已经获得了注册凭证，便可以冒充用户对被攻击网站执行某个操作。【利用了发送请求时会默认携带Cookie的特性】

特点： 

1. 一般攻击都是第三方网站发起的
2. 攻击是冒充了受害者身份提交操作，而不是直接窃取数据
3. 过程中，攻击者并拿不到受害者的身份信息，而是盗用。
4. 跨站请求可能以各种形式发生：来源是第三方的图片，超链接。

防范措施： 针对CSRF的特点 发生在第三方域名并且不能获取到受害者的cookie等信息来制定防范措施

1. 同源检测：HTTP协议中，发起请求会携带Origin Header和Referer Header，可以确定请求的来源域，如果不是合理的域名就不处理请求
2. CSRF Token：既然Cookie会自动携带，那么在校验身份的时候使用新的策略---CSRFToken，而Token无法被第三方网站发出的请求获取了
3. Cookie设置SameSite： 设置第三方网站向原网站的服务端发起请求时不携带Cookie。
+ Samesite=Strict，这种称为严格模式，表明这个 Cookie 在任何情况下都不可能作为第三方 Cookie
+ Samesite=Lax，这种称为宽松模式，比 Strict 放宽了点限制：假如这个请求是这种请求（改变了当前页面或者打开了新页面）且同时是个GET请求，则这个Cookie可以作为第三方Cookie。（默认）
+ None 任何情况下都会携带；

#### CSP【Content Security Policy】
内容安全策略，可以明确地告诉客户端浏览器，当前页面的哪些外部资源可以被加载执行而哪些不可以。

也就是默认拒绝，例外允许

常用的方式是，设置HTTP响应头，例如 <font style="color:rgb(255, 80, 44);background-color:rgb(255, 245, 245);">Content-Security-Policy: default-src 'self'; script-src https://cdn.example.com，    </font>

默认仅允许加载自身域名资源。

常用的还有 

+ <font style="color:rgb(255, 80, 44);background-color:rgb(255, 245, 245);">script-src 管理Js的脚本的加载与执行</font>
+ <font style="color:rgb(255, 80, 44);background-color:rgb(255, 245, 245);">frame-src 和 frame-ancestor【个人做项目时碰到的】</font>

#### 安全沙箱【Sandbox】
浏览器分为 渲染内核 与 浏览器内核。而我们的渲染内核不应该去进行一些关于操作系统资源访问修改的行为。因此安全沙箱便是来限制渲染内核的，如果想进行相应操作，需要通过IPC通信和浏览器内核进行数据传输。

为了保护客户端的操作系统，所以出现了安全沙箱。渲染内核只能进行HTMLCSS解析和JS的执行。

### HTTPS 深入
由于HTTP是明文传输，存在信息监听、信息篡改、信息劫持的风险，因此使用了TLS/SSL进行身份验证、信息加密和完整性校验的功能。

#### TLS/SSL工作原理
依赖三类基本算法：散列函数Hash、对称加密、非对称加密

1. 散列函数： 验证信息的完整性

特点：单向不可逆，实现了对输入数据进行计算得到哈希值，接收方同样根据数据计算出哈希值后比对两值来判断数据是完整不被篡改的。但由于中间可以修改数据后再生成新的摘要哈希值，所以要对传输的数据和哈希值进行加密

2. 对称加密：使用协商密钥对数据加密
3. 非对称加密： 实现身份证和密钥协商

综合来讲就是：客户端使用非对称加密与服务端进行通信，实现身份的校验和协商后续对称加密使用的密钥。对称加密算法就在数据传输过程中使用协商出来的密钥，对数据和摘要算法计算的哈希值进行加密。不同节点采用的对称密钥不同，保证信息只能从通信双方获取。

#### 非对称加密和对称加密的过程
1. 对称加密：加密和解密使用同样的密钥。意味着接收方和发送方共享同一个密钥来加密数据
+ 过程：
    - 密钥共享：双方共享同一把密钥，但密钥需要通过安全的方式传输或者事先就已经共享好了
    - 加密：发送方使用共享密钥对明文数据进行加密，使用的加密算法有AES/DES等
    - 数据传输：加密后的密文通过网络或者其他途径发送给接收方
    - 解密：使用同样的密钥对密文进行解密，恢复出原始数据
+ 特点：
    - 速度快：加密解密过程相对简单，执行速度快，适合大量数据加密
    - 密钥管理问题：因为双方共享相同的密钥，所以在密钥的交换和存储上需要特别小心，确保密钥的安全性。
+ 应用场景：数据加密，文件加密，大量数据传输
2. 非对称加密：使用一对密钥-公钥和私钥。公钥是公开的，私钥是保密的，仅使用者自己持有不对外传输
+ 过程：
    - 密钥生成：协商密钥【使用RSA/ECDHE】，生成自己的公钥和私钥，让对方拥有自己的公钥，得以在后续传输过程中可以使用对方的公钥进行加密。
    - 加密：发送方用接收方的公钥进行数据的加密。
    - 数据传输：加密后的密文通过网络传输给接收方
    - 解密：接收方使用自己的私钥对密文进行解密。
+ 特点：
    - 安全性高：因为私钥不涉及到暴露传输，避免了密钥泄漏的风险
    - 速度较慢：算法比对称加密复杂，不适合加密大量数据
    - 密钥管理便捷：公钥是公开的，所以密钥交换过程更加安全。
+ 应用场景： 数字签名，TLS加密，数字证书等场景。



#### 数字证书
数字证书存在的意义是：为了保证我们收到的信息来源是可靠的，所以需要通过数字证书来解决这个问题。

过程：

使用哈希算法对公钥和其他信息进行加密，得到一个信息摘要，然后让CA使用私钥对信息摘要进行加密形成签名。将原始信息和签名合在一起称为数字证书。

当接收方接到数字证书后，根据原始信息使用同样的Hash算法生成摘要，然后使用CA的公钥对签名进行解密，得到将两个摘要值进行比对，来判断信息是否被更改了

数字证书解决了身份真实性的问题。当客户端收到服务器证书后，会进行**链式校验**：

1. 首先，客户端提取证书内容计算 Hash 值；
2. 然后，找到签发该证书的 **CA 公钥**，去解密证书上的**数字签名**，对比两者 Hash 是否一致。如果一致，证明证书未被篡改且确实由该 CA 签发。
3. 接着，客户端会**一级一级向上追溯**，用同样的方法验证 CA 证书的合法性，直到匹配到操作系统或浏览器内置的**根证书（Root CA）**。
4. 如果签名校验失败、证书过期、或者无法溯源到可信根证书，浏览器就会弹出安全警告并中断连接。”



#### TLS握手过程【RSA版本】
1. 客户端向服务器发送请求：请求中包含使用的协议版本号、生成的随机数A，以及客户端支持的加密方式
2. 服务端收到请求，确认加密方式，给出服务器的数字证书【包含了服务器的公钥】，和生成的随机数B。
3. 客户端根据数字证书的公钥，可以得出服务器的数字证书有效，身份未被篡改【操作系统和浏览器都内置了根证书，客户端一级一级向上寻找，用上一级的公钥去解密服务器证书上的数字签名，如果对得上，再去认证上一级的数字证书是谁签发的，直到找到内置的可信根证书。如果签名不符合或者找不到，就无法进行后续建立连接过程】。然后使用数字证书的公钥，加密一个新的随机数C并发送给服务端，同时携带了所有内容的Hash值用来让服务器做校验数据未被篡改。
4. 服务端使用私钥进行解密，解密随机数C并计算Hash值，计算Hash值和携带过来的Hash值进行比对，检验数据有没有被篡改过。
5. 此时双方各拥有ABC三个随机数和协商好的加密方法，据此计算出对话密钥，作为后续数据传输过程中使用的密钥。而且保证里对称加密的密钥不会暴露出来，保证了安全和速度。



现在主流使用的是ECDHE的算法，保证了向前安全性【如果RSA中的服务端密钥被泄漏出来，会导致之前的对话内容都可以被窃取】而ECDHE算法是每次握手都会生成临时密钥，即使私钥泄露，以前的数据依然安全。

同时HTTPS如果用户在首次访问时就被劫持（SSL Stripping），或者攻击者诱导用户安装恶意根证书，HTTPS 也会失效。

#### TLS握手过程【ECDHE版本】
1. 客户端向服务端发起请求携带随机数A
2. 服务端回应临时公钥，保存私钥，携带随机数B，同时保留CA校验身份的响应操作
3. 客户端回应临时公钥，保存私钥
4. 双方根据对方的公钥和自己的私钥计算出同一个参数，结合随机数AB生成最终的对话密钥

#### 补充
HTTPS握手过程复杂，所以第二次访问可以根据Session ID，实现会话复用

+ SessionID，服务器把密钥存在内存中，存下对应的ID，下次带着ID直接用
+ SessionTicket： 服务端把密钥加密后，发给客户端保存，下次客户端直接带着Ticket过来，服务端解密后直接开始加密通信，实现1-RTT或者0-RTT。

### JWT
JSON Web Token：用于在各方之间安全地传输信息，是一种开放标准，一个经过数字签名的令牌。是用户在登录后，服务器生成并发送给客户端。客户端在后续请求中携带此令牌，服务器验证它的有效性和是否过期来决定是否信任用户。

#### 结构
1. Header包含令牌类型和签名算法 Base64Url（Header）
2. Payload包含关于实体的数据陈述【比如userId这种】但不能保存敏感信息，因为token并不会加密
3. Signature，将编码后的header和payload密钥根据指定的头部算法计算得出的。用于计算令牌的完整性和来源可信

#### 局限性
1. 没有过期时间，一旦签发无法撤销，如果token被盗那么会在过期前一直有效，除非维护黑名单。所以要设置合理的过期时间
2. 敏感信息泄漏：payload中不能存放其他敏感信息

#### RefreshToken机制
为了解决JWT无法撤销和过期时间的问题，所以使用双Token机制

1. Access Token，短期有效，用于实际的API调度
2. Refresh Token，长期有效，用于获取新的AccessToken

保证了用户不用频繁登录和即便获取了accessToken影响时间也很短。**如果refresh 窃取了怎么办？**









#### 使用场景
1. 单体应用Session更简单可靠，
2. 微服 或务/支持移动端，JWT更合适。



结合Token 类型、安全风险、业务场景，直接给出选型结论+落地规则，区分 AccessToken、RefreshToken。

一、核心结论（生产通用方案）

1. RefreshToken：优先放 HttpOnly + Secure Cookie（绝对首选）
2. AccessToken：优先放 请求头（Header）  
二、分开详解 & 优缺点、风险
3. RefreshToken → 推荐：Cookie（HttpOnly + Secure + SameSite）

原因

• 防 XSS 攻击：HttpOnly 禁止 JS 读取，前端脚本偷不走，解决最大威胁。

• 浏览器自动携带，无需前端手动维护，刷新逻辑更简单。

配置强制要求（缺一不可）

• HttpOnly: true：JS 无法访问

• Secure: true：仅 HTTPS 下生效

• SameSite=Lax/Strict：防御 CSRF

• 合理过期时间：7~30天

风险 & 应对

Cookie 天然面临 CSRF，靠 SameSite + 后端校验 Referer/Origin 双重防护即可，成本远低于 XSS。  
不建议放 LocalStorage/SessionStorage：XSS 直接窃取，高危。  
2. AccessToken → 推荐：Header（Authorization）

标准格式：  
Authorization: Bearer ${token}  
原因

1. 生命周期短（5~15分钟），就算泄露，危害窗口期极短。
2. 放在 Header 不会被浏览器自动携带，规避 Cookie 带来的 CSRF 风险。
3. 适配性强：移动端、小程序、第三方客户端、前后端分离架构通用。
4. 方便前端统一拦截、过期判断、统一加请求头。

缺点 & 应对

• 存在 XSS 被盗 风险：  
应对：缩短有效期 + 前端做好 XSS 防御（过滤输入、CSP 策略）。  
不建议 AccessToken 也放 Cookie：放大 CSRF 风险，没必要。  
三、两种特殊场景选型

场景1：纯移动端（App/小程序）

无浏览器 XSS、CSRF 困扰，两种都可行：

• AccessToken / RefreshToken 都可存在客户端安全存储区（App 专属沙盒）

• 请求统一走 Header，业界通用做法。

场景2：老旧项目、必须全站用 Cookie（传统服务端渲染）

• 双 Token 全部放入 Cookie

• 严格开启 HttpOnly + Secure + SameSite

• 后端加强 CSRF 校验（加 CSRF Token）

场景3：跨域场景（前后端分离、多域名）

• RefreshToken Cookie：配合 SameSite=None + Secure（跨域必备）

• AccessToken 依旧放 Header，不受跨域 Cookie 限制。  
四、对比表（一目了然）  
令牌类型 推荐位置 主要防御 主要风险   
RefreshToken HttpOnly Cookie XSS CSRF（靠SameSite防御）   
AccessToken Header(Bearer) CSRF XSS（靠短时效防御） 

五、最简落地规范（直接照着用）

1. Web 前端（浏览器）标准方案

◦ 登录后：

◦ RefreshToken → HttpOnly Cookie

◦ AccessToken → 前端内存/变量存储，每次请求放到 Authorization Header

◦ Access 过期：前端自动调用刷新接口，浏览器自动带上 Cookie 里的 RefreshToken。

2. 绝对禁止

◦ RefreshToken 存入 localStorage / sessionStorage

◦ 生产环境关闭 Secure、HttpOnly

3. 补充：如果业务允许单设备登录 + 滚动刷新，搭配这套存储方案，安全等级拉满。  
六、一句话总结

长时效、高价值的 RefreshToken 锁在 Cookie 里防 XSS；短时效、高频使用的 AccessToken 放 Header 防 CSRF。

### 模块化
模块化： 指的是我们在开发时，按照一定的规范【代码复用性】将一个复杂的、大的程序封装成几个模块也就是几个子文件，同时暴露出来一些接口方法，供外部其他模块通信/调用

而当我们一个模块要引用多个模块时，可能会发生请求过多导致浪费的情况，或者是因为不了解他们的依赖关系而导致加载先后顺序混乱的情况，此时便需要模块化规范来解决：

#### CommonJs
Node.js使用的模块化规范，用于服务器编程，模块文件一般都存在于本地硬盘，加载起来比较快，所以同步加载就可以。

1. 在服务器端，模块的加载是运行时同步加载，也就是代码执行到哪里，哪里的模块就会被加载，而且加载后的模块内容会被缓存，如果想让模块再次加载，需要清空缓存
2. 通过module.exports和require关键字来导出导入。
3. 代码运行在模块作用域而不是全局作用域
4. 加载机制：导入的是**被导出的值的拷贝【浅拷贝】**

****

#### AMD
浏览器环境下老版本的模块化规范，如果是浏览器环境要从服务器加载模块，就使用异步的AMD规范

1. 使用require.js用于客户端的模块管理，遵守AMD规范，define将代码定义为模块，require实现代码的模块加载



#### CMD
与AMD类似，但CMD推崇懒加载，对于依赖的模块，AMD是提前执行，也就是依赖的内容在自己的代码执行前就执行一遍，而CMD是执行到该依赖处才执行

#### UMD
其实是通过检测当前使用环境，决定模块化的定义方式，比如说浏览器就使用amd，服务端就使用CommonJs......

因为this在浏览器中指的是window，node中指的是global，所以做到了将各种模块化定义都兼容

#### ES6 ESModule
设计思想是，尽量的静态化，使得在编译时就能确定模块的依赖关系和输入输出的变量。区别与CommonJs和AMD都是只能在运行时确认的。

1. 使用export/import实现导出导入
2. 加载机制：导入的值是导出值的引用。
3. 编译时输出接口



#### CommonJS和ES Module的区别
1. CommonJs加载的是一个对象，即module.exports的属性，该对象只有在脚本运行完才会生成
2. 而ESM不是对象，对外接口是静态的定义，是确定好了的引用，在代码静态解析阶段就会生成
3. CommonJS的动态，体现在可以在任何地方require某个模块，因为是函数调用，所以很灵活
4. ESModule的静态，体现在必须在模块顶层使用，不能动态出现，使得依赖关系在编译时可以被完全分析出来。而ESM支持TreeShaking便是因为，我们在编译阶段就可以确定，那些export的内容没有在任何地方被import过，从而就可以在打包文件中移除。

3. Webpack的性能优化
+ 代码分割【减少打包体积】：默认情况下，所有的JavaScript代码（业务代码、第三方依赖、暂时没有用到的模块）在首页全部都加载，就会影响首页 的加载速度；代码分离可以分出更小的bundle，以及控制资源加载优先级，提供代码的加载性能；通过入口文件手动配置分离代码 / splitChunksPlugin插件去重
+ tree-shaking【减少打包体积】： <font style="color:#000000;">配置 optimization.usedExports 为 true，启动标记功能。标记了未使用的代码，Tree Shaking 就会将这些代码从最终的打包结果中删除。未使用的模块和代码块被删除，最终的打包文件只包含被使用的部分，从而减小了文件的大小。</font>
+ CDN【减少打包体积】： 打包所有静态资源，放到CDN服务器，用户资源都通过CDN服务器加载。通常配合 `externals` 配置使用。告诉 Webpack：“React、Lodash 这些大库不要打包进 bundle，我在 HTML 里用 `<script>` 标签从 CDN 引入”。这样能大幅减小打包体积。
+ <font style="color:#000000;">使用cache-loader 进行缓存【提高打包速度】：在一些性能开销较大的</font>`<font style="color:#000000;">loader</font>`<font style="color:#000000;">之前添加</font>`<font style="color:#000000;">cache-loader</font>`<font style="color:#000000;">，以将结果缓存到磁盘里，显著提升二次构建的速度。注意：保存和读取这些缓存文件也会有一些时间开销，所以只对性能开销较大的</font>`<font style="color:#000000;">loader</font>`<font style="color:#000000;">使用此</font>`<font style="color:#000000;">loader</font>`

### 虚拟DOM深入理解
#### 虚拟DOM的概念
虚拟DOM本质其实是JS对象，它通过树状结构来描述真实DOM，使得UI可以在内存中进行抽象和表示。而在Vue和React中，虚拟DOM被用于更高效地更新和渲染真实DOM。

它被设计出来的目的是，可以实现跨平台能力和尽可能减少操作DOM的次数【diff算法】



#### 虚拟DOM出现的意义
1. 对于前端的性能优化，很重要的一点就是，我们要尽可能减少操作DOM的次数，因为频繁操作DOM，会造成浏览器的重排和重绘，对性能损耗比较大。因此虚拟DOM存在的一个非常大的意义就是，尽可能一次性地将差异一次性地更新到DOM中
2. 使用虚拟DOM之后，我们也不需要手动操作DOM了，提升了开发效率
3. 还可以实现跨平台，比如Node.js中不存在DOM，如果想实现SSR服务器渲染，那就需要借助VirtualDOM。

#### 虚拟DOM的解析过程
1. 构建虚拟DOM：在运行时，Vue将template转换为虚拟DOM
2. 比对虚拟DOM：当数据变更时，Vue重新生成一个新的虚拟DOM，vue会将新旧虚拟DOM树进行比较【通过核心的diff算法】
3. 更新真实DOM：根据diff运算的结果，Vue针对变更部分生成真实的DOM更新逻辑，并将变更应用到真实DOM上。

#### Vue的diff算法【逐层比较、类型判断、Key使用、同级比较来优化】
核心思想：

1. 树的递归比较：从根节点开始，递归地对比新旧虚拟DOM树，通过DFS方式进行逐层比较
2. 同层比较：只对同一层级的节点进行比较，如果节点类型不同，则直接替换
3. 节点的复用和更新：如果节点类型相同，检查属性和子节点的变化，更新属性并且递归地对子节点进行比较。

Vue2 和 Vue3 的Diff算法比较：

1. Vue2 是 双端diff算法：同时从新旧两棵树的两端向中间移动。此种算法在当元素从中间插入或者移除时效率非常低

<img src="https://cdn.nlark.com/yuque/0/2026/png/55003070/1774788696381-15d16e6d-83ba-4550-bff4-f2fb295e0406.png" width="216" title="" crop="0,0,1,1" id="u3cd960b3" class="ne-image">

2. Vue3 的优化：
    1. 静态标记（PatchFlag）：在编译的时候对动态节点打上不同的静态标记，用于标记节点上的那些属性是动态的。这样在运行时，针对性地比对和更新节点的动态部分，提高diff的效率
    2. 静态提升（Hoisting）：在编译阶段识别并提升静态内容，将其转换为不变的常量，后续更新时直接使用，避免了重复创建和比对的开销。
    3. 块树（Block Tree）优化：Vue3中引入了块的概念。块内包含收集的所有动态节点，更新时只需要遍历块中的动态节点列表，而不需要遍历整个模版树
    4. 最长递增子序列算法：找到保持相对位置不变的最长节点序列，只移动必要的节点

#### 使用虚拟DOM一定更快吗
虚拟DOM的优势体现在它的更新算法和状态管理上，开发时可以高效地写出响应式页面，不需要手动优化DOM操作，diff算法和批量更新机制可以提升大部分情况的性能，特别是复杂、频繁变化的用户页面。

但是有些情况，真实DOM会比虚拟DOM性能更好：

+ 首次渲染大量DOM时，由于虚拟DOM需要先构架大量JS对象，会比直接插入慢一点。

### template编译原理
template部分是无法被浏览器解析并渲染的，

+ 解析阶段：所以会对template使用正则表达式进行解析，得到标签、指令、属性等转化为抽象语法树AST。
+ 优化阶段：遍历AST，找到静态节点并标记，方便在页面重渲染的时候进行diff比较可以直接跳过这些静态节点的，优化性能
+ 生成阶段：将最终的AST转化为render函数字符串。render函数生成虚拟DOM，vue比较新旧虚拟DOM，用最小移动次数将差异更新到真实DOM。
+ setup数据绑定：在compositionAPI中，setup返回的数据、方法、计算属性会被绑定到template中形成响应式依赖。数据变化时通过依赖追踪机制触发虚拟DOM更新。实现视图的自动刷新。

### MCP（Model Context Protocol）
模型上下文协议，标准化AI模型与外部工具/数据源的连接方式

解决的问题：

+ 工具接入碎片化：每个工具不同接口
+ 上下文传递困难： 模型与工具数据格式不统一
+ 生态封闭：各平台工具不互通

MCP可以将各种各样的接口数据，根据协议封装成我们规定好的数据结构，便与模型直接调用。

API 是 **Point-to-Point（点对点）** 的强耦合；MCP 是 **Bus Architecture（总线架构）** 的标准化。API 关注的是“怎么传数据”，MCP 关注的是“如何让模型理解这些数据并自主选择工具”。

Agent调用MCP：

+ **第一步：感知（Discovery）** Agent 通过 MCP 协议，知道现在有哪些“外部上下文”可用（比如：我知道有一个 `github_issue` 的资源，和一个 `send_email` 的工具）。
+ **第二步：获取上下文（Context Retrieval）** 当用户问“帮我总结这个 Issue”时，Agent 发起 MCP 请求。MCP Server 把 GitHub 里的非结构化数据，转变成**规范化的文本（Context）**喂给模型。
+ **第三步：决策与执行（Action）** 模型看了上下文后，决定调用 Tool。它输出一个符合 MCP 规范的指令，由 MCP Server 去真正执行那个 Tool（比如发邮件），最后把结果再返回给模型。

#### 冒泡排序
<font style="color:rgb(37, 41, 51);">通过相邻元素的比较和交换，使得每一趟循环都能找到未有序数组的最大值或最小值。</font>

function bubbleSort(arr) {
  const len = arr.length;
  for (let i = 0; i < len; i++) {
    for (let j = 0; j < len - i - 1; j++) {
      if (arr[j] > arr[j+1]) {
        const tmp = arr[j];
        arr[j] = arr[j+1];
        arr[j+1] = tmp;
      }
    }
  }
  return arr;
}

const arr = [8,3,4,1,7,5,6,2];

function selectSort(arr) {

    let minIndex = i;

### 手撕复盘
给定一个对象 `components`，它的键表示组件名称，值是一个数组，表示该组件所依赖的其他组件列表。 请编写一个函数 `resolveDependencies(components)`：

1. **如果没有循环依赖**：输出一个一维数组，表示安全的加载或执行顺序。**要求：被依赖的组件必须排在依赖它的组件之前。**（例如 A 依赖 B，则 B 必须在 A 之前出现）。
2. **如果存在循环依赖**：检测出该循环，并输出一个包含循环依赖路径的数组（例如 `['A', 'B', 'C', 'A']`）。

```typescript
const components = {
  'A': ['B', 'C'],
  'B': ['C'],
  'C': [],
  'D': [],
}
// 期望输出: ['C', 'B', 'A', 'D'] 或 ['C', 'D', 'B', 'A'] (顺序只要满足依赖前置即可)

const components = {
  'A': ['B'],
  'B': ['C'],
  'C': ['A'],
  'D': []
}
// 期望输出: ['A', 'B', 'C', 'A'] (或者任意循环闭环节点)
```

面试官说，是解决react18相关的循环依赖，用拓扑排序/图论来解决该问题

>  React 18 的 **Suspense**、**并发渲染（Concurrent Mode）** 以及 **React Server Components (RSC)** 的底层实现中，组件树的渲染顺序、数据请求的依赖顺序以及按需加载的 Chunk 依赖，本质上都是一个**有向图**。如果存在 A 依赖 B（比如等待 B 加载完毕），而 B 又间接依赖 A，就会造成渲染死锁。因此，框架在编译或运行时需要具备检测循环依赖的能力，并按照正确的先后顺序去解析组件或模块
>

```javascript
/**
 * @param {Object} components 传入的依赖对象
 */
function resolveDependencies(components) {
    const result = [];
    const visiting = new Set();
    const visited = new Set();
    let cyclePath = [];
    const dfs = (node, path) => {
        if (cyclePath.length > 0) return;
        if (visiting.has(node)) {
            const cycleStartIndex = path.indexOf(node);
            cyclePath = [...path.slice(cycleStartIndex), node];
            return;
        }
        if (visited.has(node)) return;
        visiting.add(node);
        path.push(node);

        const dependencies = components[node] || [];
        for(const dep of dependencies) {
            dfs(dep, path);
        }
        path.pop();
        visiting.delete(node);
        visited.add(node);
        result.push(node);
    }
    for(const node of Object.keys(components)) {
        if (!visited.has(node)) {
            dfs(node, []);
        }
    }
    if (cyclePath.length > 0) {
        return cyclePath;
    }
    return result;
}
```

### 八股复盘
#### 重绘重排【细节版本】：
1. 回流/布局/重排：

由Render树计算每个 可视节点在页面上的几何属性的过程，因为需要计算位置和几何信息，会引发大量计算非常消耗性能

当节点位置或者大小发生改变的时候会触发回流

<img src="https://cdn.nlark.com/yuque/0/2026/png/55003070/1774405953891-65760f3f-5be5-4d4a-b59c-25dd19f8a23b.png" width="501" title="" crop="0,0,1,1" id="u13c3546e" class="ne-image">



2. 重绘：

浏览器在不需要重新布局的情况下，将可视部分重新绘制在屏幕上的过程

当元素属性改变，但改变不影响布局的时候，会触发重绘

<img src="https://cdn.nlark.com/yuque/0/2026/png/55003070/1774406212025-22f336ba-c4be-4a88-bf93-f8ef660826bb.png" width="342.5" title="" crop="0,0,1,1" id="u8265e91a" class="ne-image">



3. 修改display: none/ visibility: hidden/ opacity: 0 都是否分别会引起重排/重绘 
    1. display：none： 元素从render树上被移除，导致页面几何结构发生变化，引起重排 也因此必然引起重绘
    2. visibility：hidden： 元素仍然在render树上，占据原本的物理空间，只是像素不再被绘制到屏幕上，元素由可见 -> 不可见，浏览器需要更新画布，因此不引起重排、只引起重绘。
    3. opacity： 0 ： 元素仍然占据空间，但更多是**合成**阶段的处理，不会引起重排，如果该元素被提升到了独立的合成层，修改透明度只会触发GPU的Alpha通道合成，不会引发CPU的重绘，而且opacity设为0，点击该区域依然可以触发JS事件，而前两者不可以

修改 `opacity` 是否触发重绘，取决于该元素是否拥有**独立的合成层**。如果有，则仅触发 GPU 的 **Composite（合成）** ；如果没有，由于它与其他元素共享同一个位图，必须通过 **Repaint（重绘）** 来重新计算像素混合结果

#### flex布局的详细说明：
弹性布局，可以用来为盒状模型提供最大的灵活性。是css3中新增的一种布局方式，

可以通过将一个元素的display属性值设置为flex，该元素是flex容器，而他的所有子元素都变成flex项目。

一个容器默认有两条轴，一个是默认的水平主轴，另一个的与主轴垂直的交叉轴

设置在容器的属性：

1. flex-direction：决定主轴方向
2. flex-wrap： 一条轴线排不下元素如何换行
3. flex-flow： 1.2. 的简写 默认值为 row nowrap
4. justify-content： 主轴上的对齐方式
5. align-item： 交叉轴上的对齐方式
6. align-content： 多根轴线的对齐方式，如果项目只有一根轴线，该属性不起作用//只有当flex-wrap的属性值不是nowrap的时候才起作用。

设置在项目的属性：

1. order： 定义项目的排列顺序，数值越小，排列越靠前，默认为0
2. flex-grow： 项目的放大比例默认0，有空余空间 可以设置放大比例 **为0表示不放大**
3. flex-shrink： 项目的缩小比例默认1，空间不足可以缩小 **为1表示空间不足时缩小**
4. flex-basis： 分配多余空间之前，项目占据的主轴空间，默认为auto，即项目本来的大小
5. align-self：允许单个项目有与其他项目不同的对齐方式，可覆盖align-items属性
6. flex：flex-grow，flex-shrink，flex-basis的缩写，默认 0 1 auto

> `<font style="color:rgb(6, 10, 38);">flex: 1</font>`<font style="color:rgb(6, 10, 38);"> 是 </font>`<font style="color:rgb(6, 10, 38);">flex-grow: 1; flex-shrink: 1; flex-basis: 0%;</font>`
>
> 1. `**flex-grow: 1;**`
>     - 这决定了当容器有剩余空间时，该项目是否会放大以填充这些空间。
>     - 值为 `1` 表示该项目会与其他 `flex-grow` 值为正数的兄弟项目，按比例分配所有剩余空间。
> 2. `**flex-shrink: 1;**`
>     - 这决定了当容器空间不足时，该项目是否会缩小。
>     - 值为 `1` 表示该项目在必要时会按比例收缩，以避免溢出容器。
> 3. `**flex-basis: 0%;**`
>     - 这定义了项目在分配剩余空间之前的初始主轴尺寸。
>     - 值为 `0%` 是一个关键点，它意味着浏览器在计算空间分配时，会忽略该项目自身的内容宽度，将其初始大小视为0。这使得 `flex: 1` 的元素能够完全根据容器的剩余空间来分配大小，从而实现“填满剩余空间”或“均分空间”的效果。
