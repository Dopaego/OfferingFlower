# Agent基础知识

## 八股问题

### 1. Transformer 是什么
她是一种处理序列数据的 神经网络架构, 可以把一串Token转换成一串 包含上下文信息的向量表示, 是一套架构设计.
不管是自然语言还是代码,都是序列,它们每个TOken的排列顺序都有她的意义, 而模型不能直接处理文字和她们的次序关系所对应的含义, 所以要把每个Token转换成向量.
但是初始Token Embedding的时候只能代表了Token本身, 没有次序关系, 也就无法理解上下文.
所以Transformer的任务就是 解决Embedding时没有上下文的问题, 它的核心输出也就是 每个位置的上下文化向量.
它的核心是 self-attention,负责不同Token之间信息的交换

#### 1.1 Transformer的整体结构过程
原始文本 Token化, 对Token Embedding后再添加位置信息, 执行多层Transformer, 最后得到含有上下文信息的向量

#### 1.2 一层Transformer Block有什么, 要如何执行

1. Normalization
    对隐藏向量的数值尺度进行调整, 让它更稳定化, 通常是对 前几层处理的Token 各个隐藏维度 归一化, 让它更加稳定, 不至于后续的计算会爆炸
2. Self-Attention
    负责在不同的Token之间交换信息, 使他可以从前面的变量中聚合定义
3. 残差连接
    将原始输入直接加回来, 避免深层网络丢失原始信息, 让梯度更容易传播, 是Transformer可以支持堆叠几十层甚至上百层
4. Normalization
5. MLP / FFN
    对当前Token已经聚合的信息进行非线性加工,通常对每个位置使用相同的参数: FFN(x) = W₂ activation(W₁x)
6. 残差连接

#### 1.3 Transformer和RNN的区别
在transformer出现之前, 序列模型常用RNN

- RNN: 按顺序阅读, 后面的状态依赖前面的计算,难以并行训练, 长距离信息需要很多步骤传递
- transformer: 在训练时可以同时处理多个位置, 任意两个位置可以通过Attention来直接建立联系. 主要代价是 长序列的Attention的成本较高. 

#### 1.4 Transformer的三种主要类型

1. Encoder-only
    代表模型 BERT, 每个TOken可以同时看到左右两侧, 适合于 文本分类;信息抽取;Embdeding

2. Decoder-only
    代表模型 GPT, 每个位置只能看到自己和之前的Token, 适合于自回归生成, 可以根据已有内容去预测下一个Token

3. Encoder-Decoder
    代表模型: T5, Encoder先理解输入, Decoder再通过Cross-Attention读取Encoder输出并且生成结果, 适合翻译, 摘要输入到输出的序列转换

原始 Transformer Decoder 包含对 Encoder 的 Cross-Attention，但 Decoder-only LLM 没有独立 Encoder，因此通常只有因果 Self-Attention 和 MLP[所以有些Embedding化去帮助LLM生成结果]。

#### 1.5 Self-Attention的核心任务

是Transformer中Token间信息交换的模块, 输入隐藏状态, 通过三组可学习矩阵得到 QKV 矩阵
    - Q: query当前位置需要寻找什么信息
    - K: key 每个位置可以通过什么特征被匹配
    - V: value 匹配成功后真正提供什么内容
用 Q去计算和所有 K的匹配度, 再用softmax得到关注权重, 最后按照权重 聚合 V
核心为 softmax(QKᵀ/√d)V，标准注意力对序列长度是 O(n²)。

#### 1.6 KV Cache的作用

生成下一个Token是, 历史 Token的 K \ V不需要重复计算, 可以被保存在KV Cache中, 没有 它, 每次生成一个新的 TOken 都需要重新计算整个 历史训练, 有了之后  就可以只接复用之前的 KV了

#### 1.7 Decoder-only Transoformer 中的 Causal Mask

Decoder-only 要防止模型在预测时偷懒未来的答案, 位置i看到的信息只有 1 - i-1的, i+1到末尾的 权重都设为0 而无法考虑. 

#### 1.8 理解Transformer对Agent开发的影响

首先, 长Context会增加Prefill计算, KV Cache, 首Token的延迟 和 费用成本的增加, 因此, 我们在开发时不应该把所有的信息一股脑塞给 LLM, 无用信息也会造成注意力的稀释, 所以在 Agent中有专门针对 Context管理的 开发工作. 也有RAG 去负责从仓库中找到候选信息.

AI标答:
> Transformer 是一种基于 Attention 的序列神经网络架构。它先把 Token 转成 Embedding，并加入位置信息，再经过多层由 Self-Attention、MLP、残差连接和归一化组成的 Transformer Block，最终得到每个 Token 的上下文化表示。Self-Attention 负责 Token 之间的信息交换，MLP 负责对每个位置的信息进行非线性加工。  
> Decoder-only Transformer 使用因果掩码，使位置 i 只能看到位置 1 到 i。输入已有 Token 后，模型取得最后位置的隐藏状态，通过 LM Head 得到整个词表的 logits，softmax 后选择下一个 Token，再将它拼回上下文继续生成。  
> Attention 中，Q 表示当前位置想寻找什么，K 表示各位置可以通过什么特征被匹配，V 表示真正要聚合的内容，公式是 softmax(QKᵀ/√dₖ + CausalMask)V。长度为 n 时会产生 n×n 的相关性矩阵，因此标准 Attention 对序列长度是 O(n²)，更完整地说是 O(n²d)。这也是 Coding Agent 需要通过 RAG、角色化 Context 和 Compaction 控制上下文，而不是直接放入整个代码仓库的原因。

### 2. Decoder-only Transformer 如何生成下一个 Token？Self-Attention 中 Q、K、V 的直觉和计算复杂度是什么？ [T5]

#### 2.1  Decoder-only Transformer 生成下一个 Token的全过程 

1. Token ID 转成 Token Embedding。
2. 加入位置信息，例如 RoPE。[RoPE指的是RotaryPositionalEmbedding, 通常不直接把位置向量加到 Token Embedding，而是在 Self-Attention 中根据 Token 位置对 Q 和 K 的二维分量进行不同频率的旋转。位置 m 的 Q 和位置 n 的 K 做点积时，旋转角度差与 m−n 有关，因此 Attention 分数可以自然感知相对距离和顺序。RoPE 本身不产生上下文，它只是让 Self-Attention 在聚合上下文时拥有位置信息；V 通常不旋转]
3. 依次经过多层：
    - Causal Self-Attention
    - 残差连接
    - LayerNorm/RMSNorm[用于稳定 Transformer 隐藏状态的数值尺度，通常对每个 Token 的 hidden dimension 独立归一化，不会混合不同 Token。LayerNorm 会减去均值并除以标准差，再通过可学习的 γ、β 恢复表达能力；RMSNorm 不减均值，只除以均方根，通常只有 γ，因此计算更简单。现代 Decoder-only 模型经常采用 Pre-RMSNorm，即先归一化，再进入 Attention 或 MLP，最后通过残差连接加回原隐藏状态，从而提高深层模型的训练稳定性。]
    - MLP/FFN [Transformer 中的 MLP 和 FFN 通常指同一个 Position-wise Feed-Forward Network。它对每个 Token 独立使用相同参数，经典结构是 W₂·activation(W₁x)，先从 d_model 升维到 d_ff，通过非线性激活组合特征，再降回 d_model，从而能够与输入进行残差相加。Attention 负责不同 Token 之间的信息交互，FFN 则负责对每个 Token 已聚合的上下文特征进行非线性加工。现代大模型常使用 SwiGLU 等门控 FFN，FFN 通常也占据模型的大量参数和计算量。FFN 则负责对每个 Token 已聚合的上下文特征进行非线性加工。现代大模型常使用 SwiGLU 等门控 FFN，FFN 通常也占据模型的大量参数和计算量。]
4. 取得最后一个位置的隐藏状态 hₙ。
5. 通过 LM Head 映射成词表大小的 logits。
6. 对 logits 做 softmax，得到下一个 Token 的概率分布。 softmax将logits转换为概率分布
7. 通过 greedy、temperature、top-p 等策略选择下一个 Token。
8. 把新 Token 拼回输入，继续生成，直到 EOS、停止条件或工具调用完成

#### 2.2 Self-Attention 中 Q、K、V 的直觉和计算复杂度是什么？

模型不会只做一套 QKV, 而是做多组的 Attention Head,允许模型同时从不同角度表示子空间建立关系.
直觉指的就是在当前这套QKV中的Attention Head,会对当前的query拥有的判断
计算复杂度是 O(n^2), 但这是从只关注序列长度的时候简写的, 除了这个 还要考虑模型的维度, 最后是O(n²d)

### 3. Tokenizer、Embedding、位置编码、KV Cache 分别解决什么问题？代码 Embedding 与普通文本 Embedding 的要求有何不同？

- Tokenizer 将文本离散化；
- Embedding 映射为向量；位置编码表达顺序；
- KV Cache 复用历史 Token 的注意力键值以加速自回归解码。

#### 3.1 RAG中的检索Embedding: 代码 Embedding 与普通文本 Embedding 的要求有何不同？

代码Embedding 除了对于语义的匹配,还要保存函数的结构等精确的内容, 而普通文本Embedding不需要考虑那么多

> 代码检索 Embedding 除了理解自然语言语义，还要保留标识符、错误码、语言、Symbol、作用域、AST 结构、调用关系和 Commit 等信息。纯向量检索擅长“需求描述到代码实现”的语义召回，但容易漏掉精确函数名和错误码，所以项目中使用 pgvector 召回语义候选，用全文检索补充精确 Token，再用 Codemap 扩展 import、call 和 test 等结构关系，最后通过 RRF、Rerank 和 Commit 校验装配 Context。

### 4. Temperature、top-p、seed 和模型非确定性会怎样影响规划、工具参数及评测复现？哪些环节应尽量确定性？

当模型经过transformer去选择下一个Token时, 会将logits经过softmax得到不同选择对应的概率, 而如何抽样,就会受到Temperature和top-p还有seed的影响

- Temperature: 通过缩放logits改变概率分布, Temperature越低, 概率分布变得更加尖锐, 模型也倾向于选择最高logits 的Token,特点是 输出更加稳定,更加保守, 探索性较弱. Temperature为0 的时候就表示尽量减少采样随机性, 近似于 永远选择当前最高概率的Token. 但是不代表整个系统绝对稳定, 还是会受到比如说prompt 微小差异的影响. 
- top-p: 从高到低排列Token概率, 保留累计概率刚刚达到p的最小候选集合, 也就是把剩余部分排除在外. 因此它筛选的是概率,而不是个数. 

所以综合来讲, Temperature和Top-p会互相影响, 调参时不要同时大幅修改两个参数, 根据不同的场景使用不同的Temperature

- seed: 是一个随机数,用于选择对应的Token

#### 4.1 模型的不确定性

一个Agent系统的不确定性不只来自采样

模型层:
- Temperature；
- top-p；
- top-k；
- seed；
- 模型服务实现

检索层:
- Reranker
- 查询改写
- 相同分数候选的排列
所以检索评测中应该加入稳定排序, 评测时要固定Embedding模型, Rerank版本等

工具和环境层:
- 网络请求
- API限流
- 数据库并发

编排并发层:
- Multi-Agent架构中,Agent执行速度不同, 返回结果的顺序不同

#### 4.2 结合项目,根据不同阶段调整模型的确定性

- 需求澄清: lowtemperature, 要覆盖歧义,但不能发挥需求
- Planner规划: low Temperature, 同时复杂任务要存在多候选, 稳定的同时 要保持探索替代的方案
- Locator查询改写: lowTemperature
- Executor代码生成: 低温
- Reviewer: 可使用独立视角
- Verifier: 确定性程序,必须依据真实Build/Test的结果

可以看出来我们的项目大部分都要求lowTemperatur, 因为它的使用场景毕竟是在固定好了coding style的仓库,去完成需求和coding, 自由发挥的程度是比较低的. 所以求稳, 要提高确定性, 但是在reviewer部分可以适当提高不确定性, 保证各个角度的审查都是没问题的.


### 5. Model、Agent、Agent Harness、Framework、Runtime 是什么关系？可靠性应由模型承担，还是由 Harness/Runtime 的状态、工具、验证和恢复机制承担？

- Model模型: 负责提出概率性的语义判断,她擅长处理难以用传统规则完全表达的语义问题, 它只是语言模型, 不是真正的执行者
- Agent: 围绕目标形成决策循环
- Harness: 为模型提供上下文\工具和安全约束
- Runtime: 负责真正执行\持久化\调度和恢复
- Framework: 是实现这些能力的开发抽象

模型能力决定了上线, 但是生产的可靠性是由Runtime的确定性约束兜底, 也同时避免框架层过度复杂, 而在我们的项目中, TaskContract/Zod/审批/Gate 会作为边界

#### 5.1 Agent的定义

它是围绕目标运行，能够观察状态, 选择动物, 调用工具并且根据结果继续决策的系统实体
一个Agent不一定对应一个独立模型, Agent之间的区别更在于Context,systemPrompt,Tool权限,Token预算等内容. 一个Agent的不同阶段任务可以使用不同的模型, 简单问题使用小模型, 复杂问题使用大模型

所以MultiAgent中 实现不同Agent的角色隔离应该体现在 Context管理/ 工具权限 等方面

#### 5.2 Agent Harness

包裹在Model周围, 让模型能够安全\稳定地使用Context\Tools和外部环境的一整套机制
模型本身的调用可能只是 prompt注入 -> 模型思考后的输出
而harness会讲这个过程完整化系统化,她通常包括:
- ContextBuilder: 决定本轮给模型注入什么[SystemPrompt\工具Schema\历史摘要等信息]
- ToolRegistry: 为模型声明, 可以使用哪些工具, 要包含是否幂等的信息
- Structured Output: 将模型输出约束为符合结构的JSON并通过Zod等进行运行时的验证
- Authorization/Policy: 用于判断权限, 当前工具能否使用, 是否需要审批
- sandbox: 限制文件范围,网络目标等信息
- Context与工具结果隔离: 明确标注外部信息为不可信数据, 因为可能存在PromptInjection的现象
- Validation: JSON Schema, BuildTestGate的校验,路径校验等内容
- TracingHooks: 记录Model调用, Tool调用,检索,Token耗用等情况.
Harness做出的限制都是在代码层面来强制执行规则的,而非只是在prompt中注入请勿执行危险命令等信息

#### 5.3 Agent Runtime

是负责实际运行Agent任务的执行系统.
区别于状态机, 状态机负责去定义每一个状态, 比如 判断什么满足了什么条件去进入当前的状态, 处于当前的状态下一步该做什么.
而Runtime是负责执行每一个状态定义的任务, 和执行根据不同状态进入下一步的操作
状态机提供控制规则，Runtime 执行这些规则并处理真实世界的模型、数据库和工具。
Runtime包含了状态机,除此之外还有 

- Scheduler,负责哪个Agent执行, 哪些节点可以并发, 最大并行数等工作
- Checkpoint, 将任务持久化, 当前task, 已完成节点和对应的output,剩余预算
- Cancellation, 使用AbortSignal, 将取消传播到 子Agent, 模型流, 数据库查询, Shell,
- Retry: 决定哪些错误可以重试, 如果碰到权限问题, 不再强硬重试, 429, 暂时网络错误这种可以重试

而AgentRuntime和Node.js的Runtime的区别:

- NodejsRuntime: 提供EventLoop/ V8 / IO等基础执行环境
- AgentRuntime: 提供Agent状态机\调度\工具\恢复等基础业务能力

#### 5.4 Framework

是帮助开发agent\Harness 或者Runtime的可复用框架又或者SDK.它可能提供Agent类, Tool装饰器, DAG, Graph
Framework是开发时的抽象, 而Runtime是Framework能够真正运行起来的实际执行实例.

常考框架:

- LangChain: 对Agent能力的抽象, 核心抽象了Model\Prompt\Tool\Retriever\Agent\Middleware, 他适合的场景都是比较简单的, 比如聊天, 简单的Tool Calling等
- LangGraph: 有状态Agent编排框架与Runtime,核心抽象了Edge,State,Node,Route等.它适合于的场景是长任务,复杂工作流, 但需要先设计状态和流程

这两者其实不是竞争关系, LangGraph中的某些节点,可以使用LangChain的模型和工具组件

- Llamaindex: 作为RAG的Framework,偏向于数据接入,索引,检索,contextEngineering

对话式Framework协作灵活，但过程可能发散、成本较高。
图式Framework编排更可控，适合审批、重试和恢复。

> LangChain 和 LangGraph 广义上都属于 Agent Framework，但抽象层不同。LangChain偏高层 AI 应用开发，提供模型、Prompt、Tool、Retriever、RAG 和 Agent 等组件；LangGraph偏有状态编排和 Runtime，通过 State、Node、Edge、Checkpoint 和 Interrupt 显式管理复杂流程。两者不是互斥的，通常可以用 LangChain提供能力组件，再用 LangGraph组织运行流程。除此之外，常见框架还有 OpenAI Agents SDK、Google ADK、AutoGen、CrewAI、Semantic Kernel、PydanticAI 和 TypeScript 生态的 Mastra；LlamaIndex、Haystack更偏 RAG，Vercel AI SDK 更偏流式 AI 应用层，MCP 是协议，Temporal 是通用工作流引擎。实际选型要看状态复杂度、恢复要求、人工审批、语言生态和外部副作用治理，而不是只比较框架功能数量。

> Model 是提供概率推理和生成能力的组件，它根据 Context 生成计划、代码或 Tool Call 意图，但输出不应被视为事实或授权命令。Agent 是围绕目标运行的决策实体，包含 Context 装配、模型调用、工具执行、Observation、状态更新、验证和停止条件。一个 Agent 可以使用多个模型，多个 Agent 也可以共享同一个模型。  

Agent Harness 是模型周围的工程约束层，包括 Prompt、Context Builder、Tool Schema、Zod、权限、沙箱、审批、检索和验证接口。Agent Runtime 是真正执行任务的引擎，负责状态机、调度、持久化、预算、取消、重试、Operation ID、Lease、Checkpoint 和故障恢复。Framework 则是实现这些组件的可选 SDK 或开发抽象，它不自动提供生产可靠性。  
可靠性需要分层承担。Model 负责提高计划、定位和代码生成正确的概率，决定能力上限；但权限、状态迁移、预算、幂等、副作用、恢复和最终 Gate 必须由 Harness/Runtime 的确定性代码控制。我的原则是“Model 产生 Proposal，Runtime 产生 Decision，Tool 产生 Effect，Verifier 产生 Evidence”。强 Runtime 不能把弱模型变聪明，但可以保证模型犯错时安全失败、可恢复、可审计。




### 6. Context Engineering与Prompt Engineering的区别
