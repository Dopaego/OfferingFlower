# 项目整体描述

>技术栈: TypeScript、Node.js、React、Electron、PostgreSQL/pgvector、Redis、Zod、OpenTelemetry、Vitest、Playwright [R1]

> 参与开发面向本地研发工作区的桌面端 Multi-Agent Coding Platform，实现在大型前端仓库中的知识增强定位与“需求—修改—构建—测试—PR—Stage”交付闭环。[R2]

## 职责

本质上是一个运行在开发者电脑上的AI Coding Agent,能够完成 从用户输入需求 到 交付测试链接的全流程开发. 能够实现 理解需求,定位代码,制定计划,验证结果等功能.

Snrcode 虽然是约 42 万文件、2,000 万行代码的超大型 Monorepo，但仓库规模和执行位置是两个问题。Agent 操作的是开发者本地工作树，里面包含未提交修改、本机构建环境和本地 Git 状态，因此仍然需要本地 Agent Host。  
我们将 Electron Main 定位为本地控制面，负责工作区授权、工具权限、审批、任务生命周期和 IPC 路由，而不是直接承担全仓索引和构建计算。索引、Agent 编排和构建测试通过 Worker、子进程或后端服务执行。PostgreSQL/pgvector、Redis、模型网关和可观测系统则作为共享后端能力。  
这种架构既保证远程服务能够处理知识检索和任务协调，也确保文件、Git 和 Shell 操作发生在拥有真实工作区状态的本地环境中。

## 常见问题

### 1. 大型前端仓库到底有多大

其实不只是前端项目, 他是一个react作为前端, c#作为服务端中间件的项目, 包含了bing的serp页面所有服务, 使用monorepo做管理, 近400个业务模块,而且多技术栈共存,开发起来非常困难.

### 2. 做成Electron应用会不会在"大型前端仓库"的实际开发过程中造成用户开发体验的变差, 为什么不直接Web应用:

    作为桌面级Agent, 可以选择将[需要访问本地的工作区\Git\Shell\构建工具和用户凭证] 等涉及OS交互的危险操作放在本地操作而不是走远程后端, 而Electron的Main进程刚好可以完美契合这一点. 提供了Agent Host这一点是她作为 桌面级Agent应用的优势,
    其实存在云端类似的开发助手, 但是在真正开发过程中, 如果想要修改一个云端开发的代码, 存在繁琐的修改流程, 获取云端分支并且再拉取, 而且当时团队使用的云端开发方案没有开放满足需求的自定义 MCP、仓库 Skill 和本地工具扩展能力。 在某些特殊场景比如说精确还原design, 针对自己的answer service写skill都无法实现. 因此开发时还有了当前的 electron 应用, 帮助在本地开发, 两者并不冲突.
    在实际使用的时候, 该Agent其实在使用的时候比较像Codex, 但她是针对于snrcode开发的, 云端服务端保存了关于main的信息, 每次切换分支会将diff部分发送给云端服务端, 所以虽然仓库规模比较大, 但是在开发过程中一般涉及的跨五个及以上answer开发场景比较少, 本地开发的工作树不会有太多的负担. 在这种场景下, Electron Main进程可以作为本地的控制面, 负责工作区的授权\审批等. 并不是直接承担全层的索引和构建计算.
    Electron Main进程可以作为 Agent Host 管理高权限能力, Renderer 只负责交互和展示. 

    Agent的Runtime\ 索引 \ 构建测试 还是通过 后端服务执行.
    而PostgreSQL/pgvector、Redis、模型网关和可观测系统则作为共享后端能力。  

### 3. 想做一个桌面级应用除了Electron,还有什么其他的方案,各有什么利弊

虽然Electron上手比较快,但是性能一直是比较大的问题, 而且有了ai之后, 技术栈之间的壁垒会越来越小, 因此如果让我选择同样实现一个桌面级的Agent应用, 我可能还会选择 Tauri, 它的架构不再通过Chromium 到 Node实现对os的操作, 而是通过 WebView 到 Rust Backend. 但它的插件生态不如Electron. 
除了这两个之外,还有Qt配合cpp,这个性能也很不错, 很多图形处理的软件[智驾场景]都会使用Qt开发, 不过即便有了AI,开发起来还是比较吃力, 而且Agent场景也不会对性能造成过多的压力, 所以综合下来, Qt开发的性价比也不算很高
不过不管客户端的技术栈是什么, 最核心的还是Agent Runtime + Tool生态.这方面就不会受到Electron还是Tauri的影响了

### 4. 在你的交付闭环中涉及了"需求-定位-修改-构建-测试-PR-Stage"的全流程, 那这其中,是全都用了Agent吗[T3]

并非全部使用Agent, 使用Agent的优势是可以解决步骤未知,需要探索和语义判断的任务,但它也有一定的几率会带来副作用, 也有可能解决问题的效果不够稳定, 同时调用LLM会造成 成本增加和延迟时间的增加. 
因此我们要有选择性地使用Agent, 比如在我们的交付闭环中, Git状态检查\构建\测试\审批 都是流程固定的阶段, 所以这部分应该交由确定性workflow来实现. 它们的特点都是路径稳定, 规则明确, 每次执行的步骤都具有一致性.
而需求澄清, 代码定位, 修改策略都适合于Agent.
