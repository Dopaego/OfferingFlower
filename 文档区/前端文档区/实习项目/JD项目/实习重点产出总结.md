## 一、E2E 自动化测试体系建设

### 1. 这个场景为什么需要 E2E

`mobile-tools-ui` 中的问题提报功能不是一个简单表单，它的复杂度主要来自几个方面：

- 它跑在移动端，依赖 antd-mobile 组件，很多交互是弹窗、上传、日期选择、Toast、移动端点击。
- 表单展示不是固定的，不同问题类型会展示不同时间字段，例如零部件损坏、极端天气、系统异常、碰撞事故、其他问题。
- 同一个问题类型，在不同供应商下规则也不同，例如 JD、NEOLIX、RINO 对极端天气、修路/站点搬迁是否展示结束时间有差异。
- 提交流程依赖真实接口和测试环境数据，单元测试很难覆盖“用户从进入页面到选择类型、填写描述、上传图片、选择时间、提交”的完整路径。
- 联调时经常出现“前端操作已完成但后端返回 500”“校验方式和预期不一致”“上传还没完成就提交”等问题，需要可回放的证据。

所以这个场景很适合用 E2E：它验证的不是某个函数，而是用户真实路径、前后端联调结果、移动端组件行为和业务规则组合。

### 2. 具体怎么做

在 `mobile-tools-ui` 中，E2E 体系不是只写几个脚本，而是按完整测试工程来搭建：

- 在 `playwright.config.ts` 中配置测试目录、超时时间、并发 worker、失败重试、HTML/JSON 报告。
- 使用移动端设备模拟，配置 Pixel 5 视口、触摸事件、中文 locale、Asia/Shanghai 时区，尽量贴近真实移动端使用环境。
- 在失败时保留 `trace`、截图、视频，方便后续回放定位。
- 在 `package.json` 中补齐运行脚本：
  - `npm run test:e2e`
  - `npm run test:e2e:ui`
  - `npm run test:e2e:headed`
  - `npm run test:e2e:debug`
  - `npm run test:e2e:report`
- 在 `e2e/pages` 中引入 Page Object Model：
  - `BasePage.ts` 封装通用能力。
  - `IssueFeedbackPage.ts` 封装问题提报页的元素定位和交互动作。
- 在 `e2e/specs/issue-feedback` 中按业务场景拆分测试：
  - `basic-submission.spec.ts`
  - `validation.spec.ts`
  - `time-selection.spec.ts`
  - `supplier-diff.spec.ts`
- 在 `e2e/test-data` 中维护测试车辆和图片，避免测试代码里硬编码散落。

这套结构的好处是：后续如果页面 DOM 或接口有变动，优先改 Page Object 和测试数据，而不是到每个测试用例里逐个改。

### 3. 具体例子：问题提报全流程

以“零部件损坏问题提报”为例，一个完整 E2E 流程可以拆成：

1. 进入问题提报页面，并带上车辆和供应商参数。
2. 等待页面加载完成，确认车辆信息和问题类型区域可见。
3. 选择“零部件损坏”问题类型。
4. 校验页面应展示“问题开始时间”和“预约维修时间”。
5. 填写问题描述。
6. 上传测试图片，并等待图片上传完成。
7. 选择时间。
8. 点击提交。
9. 等待 Toast 或接口响应，判断提交结果。

这个流程里有几个容易出问题的点：

- 图片上传是异步的，不能上传后立刻提交，否则可能出现图片还没拿到 URL 的问题。
- DatePicker 有弹窗动画，不能只靠固定 sleep，要等组件状态稳定。
- antd-mobile 的 TextArea、MediaUploader 可能存在多个实例，选择器必须足够稳定。
- 如果后端返回 500，需要区分是前端参数错、测试车辆不存在，还是后端环境问题。

所以 E2E 的价值不只是“点了一遍页面”，而是把这些真实交互里的异步、组件、接口、业务规则串起来验证。

### 4. 测试覆盖了哪些业务规则

当前问题提报 E2E 覆盖约 25 个用例，重点不是数量，而是覆盖维度比较完整：

- 基础提交流程：零部件损坏、系统异常、碰撞事故、其他问题。
- 表单校验：问题描述、图片上传、时间选择、图片数量限制、提交前校验。
- 时间选择规则：不同问题类型对应不同时间字段。
- 供应商差异：JD、NEOLIX、RINO 在同一问题类型下展示规则不同。

其中比较有业务含量的是时间规则和供应商差异。例如：

- 极端天气在 JD 供应商下需要开始时间和结束时间。
- NEOLIX 供应商下极端天气不展示结束时间。
- 修路/站点搬迁在 JD 供应商下展示结束时间，但在 NEOLIX、RINO 下不展示。

这些规则如果靠人工测试，很容易漏测；如果后续产品调整某个供应商规则，E2E 可以很快暴露差异。

### 5. 失败结果如何沉淀为可行动问题

`E2E-TEST-STATUS.md` 中对测试结果做了归因，而不是只写“失败 11 个”：

- 基础提交流程失败集中在 API 返回 500，但页面加载、类型选择、描述填写、图片上传、时间选择、点击提交都已完成，说明前端操作链路基本跑通。
- 表单校验失败多是因为测试预期和实际实现不一致，例如测试预期按钮 disabled，但实际可能是点击后 Toast 校验，或组件内部阻止提交。
- 后续建议也明确到行动项：
  - 检查测试车辆是否存在。
  - 查看后端 API 日志。
  - 确认提交参数格式。
  - 调整断言方式以匹配真实校验逻辑。
  - 必要时为本地测试引入 mock。

这体现的是工程化测试意识：测试失败本身不是终点，重要的是能把失败分类，并转成联调和修复路径。

### 6. 为什么要制定 data-testid 选择器规范

移动端页面大量使用第三方组件，如果 E2E 选择器依赖 class、中文文案或 DOM 层级，测试会非常脆弱：

- CSS 重构会改 class。
- 文案调整会导致 `hasText` 失效。
- antd-mobile 升级可能改变内部 DOM。
- AI 或新人写测试时容易选到错误元素。

因此沉淀了 `docs/testing/SELECTOR_GUIDELINES.md` 和 `SELECTOR_CHEATSHEET.md`，约定：

- 新功能关键交互元素优先添加 `data-testid`。
- 命名使用 `[page/component]-[element]-[type]`。
- 选择器优先级为 `data-testid` > role > label > placeholder > class。
- 对动态列表用 `data-item-id`、`data-type`、`data-state` 辅助定位。
- 对第三方组件可以用 wrapper 透传测试标识。

这件事的价值是把 E2E 从“能跑一次”变成“长期可维护”。

### 7. 可以写进总结的话

> 在 mobile-tools-ui 中参与 Playwright E2E 自动化测试体系建设。问题提报功能涉及移动端组件、图片上传、日期选择、供应商差异和真实接口联调，人工回归成本高且容易漏测。我基于 Playwright 搭建移动端 E2E 环境，配置设备模拟、失败截图/视频/trace、HTML/JSON 报告，并用 Page Object Model 封装页面交互，围绕基础提交、表单校验、时间字段展示和供应商差异编写约 25 个用例。同时沉淀 data-testid 选择器规范和测试状态报告，将失败结果归因到接口环境、前端校验或测试预期差异，提升核心流程回归和联调排障效率。

## 二、OTA 2.1 云端前端联调与测试覆盖

### 1. 这个场景为什么复杂

`ota-ui` 的 OTA 2.1 云端链路不是普通列表页，而是典型的复杂业务后台：

- 车辆选择涉及车型、站点、分页、批量添加、重复车辆冲突。
- 配置模板是树形/表格混合编辑，涉及新增、删除、移动、草稿、保存、刷新、定位。
- 配置项存在依赖关系，依赖项可能为空、无效、历史脏数据、多选或清空。
- conf 对比和预览涉及多个接口返回、弹窗状态、选中顺序和失败回退。
- 联调阶段接口频繁变化，UI 和数据结构都容易出现边界问题。

这类页面如果只靠人工点，很难覆盖所有组合；如果没有测试兜底，修一个地方很容易影响另一个操作。

### 2. 具体怎么做

在 OTA 2.1 云端联调中，围绕核心链路持续迭代：

- 任务车辆选择：更新接口调用，修复重复车辆选择逻辑。
- 配置模板编辑：支持 conf 预览、配置项新增后定位到对应部分。
- 配置项依赖：增加依赖项接口调用，支持依赖项多选。
- 配置选择弹窗：修复配置选择不同步。
- 样式和弹窗：优化弹窗高度、滚动、表格 sticky 等可用性问题。

同时通过 Vitest/Testing Library 补充测试，重点文件包括：

- `config-template-edit.test.tsx`
- `ota-task-vehicle-selection.test.tsx`
- `version-selection-modal.test.tsx`
- `vehicle-ota-history-modal.test.tsx`
- `config-template-detail.test.tsx`

测试不是只验证渲染，而是覆盖业务边界和联调中容易出错的行为。

### 3. 具体例子：配置模板编辑为什么需要测试

配置模板编辑里，一个“新增配置项”看似简单，实际牵涉很多状态：

1. 当前选中了哪个文件。
2. 当前选中了哪一行。
3. 新增的是根节点、兄弟节点还是子节点。
4. 后端返回的 `order` 是否连续。
5. 保存成功后是否刷新当前文件。
6. 刷新后是否能定位到后端返回的 `itemNo`。
7. 如果保存失败，草稿行是否还保留、是否允许重试。
8. 如果快速重复点击，是否会重复提交。

测试中覆盖了：

- 新增后滚动定位到返回的 itemNo。
- 后端 order 稀疏时仍按相对移动契约调用接口。
- 草稿保存失败时保持可编辑。
- 快速重复点击只提交一次。
- 删除后再次新增使用最新后端 order。
- 切换文件时如果有未保存输入，需要弹确认。

这些都是人工测试很容易漏掉，但线上一旦出问题会影响配置准确性的场景。

### 4. 具体例子：车辆选择为什么需要测试

OTA 任务车辆选择中，用户会按车型、站点等条件筛选车辆，然后批量加入待升级列表。这里容易出现的问题包括：

- 站点多选后，接口参数是否按数组提交。
- 重置筛选后，站点是否清空并重新请求。
- 滚动到底部是否按 page size 加载下一页。
- 已加入待选列表的车辆，在重新搜索后是否仍保留。
- 后端返回 null data 时，表格是否清空而不是保留旧数据。
- 冲突检查失败时，是否展示后端错误并阻止加入。

测试中覆盖这些点，可以避免联调阶段“筛选条件看起来选了，但接口参数不对”“列表刷新后用户选择丢失”“后端失败但前端误加入”等问题。

### 5. 这个产出的价值

这部分价值可以从三个角度讲：

- 对业务：保障 OTA 任务选择和配置模板编辑这些核心链路的正确性。
- 对工程：把复杂状态和边界行为写成自动化测试，减少回归成本。
- 对联调：接口变更后可以快速发现参数、状态刷新、失败回显是否被破坏。

### 6. 可以写进总结的话

> 在 OTA 2.1 云端项目中参与任务车辆选择、配置模板编辑、conf 对比/预览、配置项依赖等复杂链路开发和联调。由于配置模板涉及树形表格、新增/删除/移动、草稿保存、后端 order、刷新定位和依赖项选择等大量边界状态，我通过 Vitest/Testing Library 补充关键回归测试，覆盖配置项新增后定位、依赖项多选/清空、重复车辆冲突、筛选参数提交、接口失败回显、弹窗滚动布局等场景，用自动化测试降低联调阶段高频变更带来的回归风险。

## 三、移动端点位选择链路优化

### 1. 这个场景为什么重要

`mobile-tools-ui` 中 JKC 建单点位选择是移动端任务创建链路的一部分。用户要选择车辆停靠点或历史下单点位，如果这个流程体验不好，会直接影响建单效率。

这个场景的复杂点在于：

- 点位来源可能包括搜索结果、历史点位、用户点位、车辆停靠点。
- 接口返回的数据结构中可能存在空对象或部分字段缺失。
- 点位是否可用由 `canUse` 字段决定，不能只看是否展示。
- 接口文档会变更，例如历史下单点位需要新增车型参数。
- 移动端空间有限，空状态、禁用态、点击态都要清楚。

### 2. 具体怎么做

围绕点位选择链路，做了几类工作：

- 新增历史点位页面，让用户不必每次都重新搜索常用点位。
- 新增无搜索结果占位图，避免空白页面让用户误以为加载失败。
- 优化搜索结果列表、历史点位列表和点位选择容器。
- 根据接口文档变更，在查询历史下单点位时补充车型参数。
- 更新 `canUse` 字段处理逻辑，不可用点位展示禁用态，并阻止点击选择。
- 为 points 数组中的空对象增加防御处理，避免 `point.userPoint` 或 `point.carStopPoint` 为空时报错。
- 将 SelectPosition 下局部 `api.ts`、`types.ts` 按项目规范迁移到统一业务 fetch 和 type 目录。

### 3. 具体例子：空对象为什么要兜底

原本列表渲染里会直接访问：

```tsx
point.userPoint.canUse
point.carStopPoint.canUse
point.carStopPoint.title
```

如果接口返回数组中混入 `{}` 或部分字段为空，页面就会直接运行时报错，用户看到的不是某个点位不可用，而是整个页面崩掉。

修复这类问题的思路不是简单加一个 if，而是要明确：

- 哪些数据是渲染列表的最低要求。
- 不满足最低要求的点位是否应该过滤。
- 不可用点位是展示禁用态，还是不展示。
- 点击时是否再次判断，避免只靠样式禁用。

这体现的是前端对接口异常数据的防御能力。

### 4. 具体例子：为什么要迁移 API 和类型

`SelectPosition` 页面如果自己维护 `api.ts` 和 `types.ts`，短期能跑，但长期会有几个问题：

- 其他页面复用点位接口时找不到统一入口。
- 类型定义和接口定义散落在页面目录，不符合项目已有分层。
- 接口文档更新时，容易只改一个页面，漏掉其他引用。
- 页面组件承担过多职责，不利于维护。

迁移到统一 fetch/type 结构后，页面更专注于交互，接口和数据结构由统一层维护，符合项目整体规范。

### 5. 可以写进总结的话

> 在 mobile-tools-ui 中优化 JKC 建单点位选择链路。该场景涉及搜索点位、历史点位、车辆停靠点、点位可用性和接口异常数据，直接影响移动端建单效率。我新增历史点位和无结果状态，跟进接口文档补充车型参数，完善 `canUse` 禁用逻辑，并对接口返回空对象做防御处理，避免异常数据导致页面崩溃。同时将 SelectPosition 局部 API 和类型定义迁移到项目统一 fetch/type 结构，提升模块分层和后续维护性。

## 四、路测工具 PRD 拆解与前端骨架落地

### 1. 这个需求为什么不是普通页面开发

路测工具是一个跨系统需求，不是单个后台页面：

- `operation-platform-ui` 负责路测配置和管理。
- `rover-op-ui` 或监控系统可能负责单车页入口、实时测评、回放承接。
- 车端/安卓端可能负责发起路测、执行任务、展示状态。
- 后端需要提供测试项、地图图层、路测方案、测评记录、缺陷提报等接口。
- 权限侧需要新增菜单权限、页面权限、按钮权限。

因此它首先需要做的不是直接写代码，而是把 PRD 拆成可执行的前端交付清单，并识别哪些属于当前项目，哪些需要其他项目或后端补齐。

### 2. 具体怎么做

基于 PRD 和接口文档，整理了：

- 5 类新增页面：
  - 路测测评管理。
  - 路测测试项管理。
  - 路测地图设置。
  - 路测方案管理。
  - 缺陷提报配置。
- 每个页面的查询条件、列表字段、弹窗字段、操作按钮和交互规则。
- 公共组件抽象：
  - `ProductionFactorySelect`
  - `UserPicker`
  - `OperationRecordDrawer`
  - `VoidConfirmModal`
  - `DraggableCheckList`
- 类型定义：
  - `roadTestEvaluation`
  - `roadTestItem`
  - `roadTestMap`
  - `roadTestPlan`
  - `defectReportConfig`
- 接口封装：
  - 列表、新建、编辑、删除、作废、操作记录、绑定校验等。
- 联调缺口：
  - 真实接口。

  - 监控系统跳转协议。
  - 浮窗测评归属。
  - 车端/安卓端承接。

同时在 `operation-platform-ui` 中落地了页面目录、路由、公共组件、类型文件和接口骨架。

### 3. 具体例子：路测方案管理怎么拆

以“路测方案管理”为例，PRD 里的描述不能直接变成代码，需要拆成更细的前端任务：

- 列表查询：
  - 路测方案名称。

## 五、地图坐标与高精地图图层问题沉淀

### 1. BMapGL 坐标偏移为什么难排查

路测地图中曾出现鼠标点击位置和实际绘制覆盖物位置固定偏移的问题。这个问题难点在于：

- 页面看起来是“绘制逻辑错了”，但实际可能是地图坐标系问题。
- BMapGL 中底图、点击事件、覆盖物绘制可能涉及不同坐标系。
- Demo 中没有偏移，但项目中有偏移，需要对比初始化配置、事件绑定、地图容器和坐标类型。
- 偏移在中国区域明显，国外或默认坐标系下可能不复现。

### 2. 具体怎么定位

排查时对比了几个方向：

- 是否是 `clientX/clientY` 到地图像素转换的问题。
- 是否是 `e.point` 本身有偏移。
- 是否是地图初始化和绘制事件绑定时机不同。
- 是否是 `map.disableDragging()` 或 displayOptions 影响。
- 是否是 Demo 和项目使用的坐标系不同。

最终沉淀的根因是：

- 设置 `coordType: BMAP_COORD_GCJ02` 后，地图底图按 GCJ02 加载。
- 但覆盖物绘制时仍按 BD09 渲染。
- 底图和覆盖物坐标系不一致，导致中国区域内出现约 500-800 米固定偏移。
- RoadTestMap 不应直接设置 GCJ02，应使用 BMapGL 默认 BD09；如果后端返回 GCJ02，需要在数据进入和离开地图时做转换。

### 3. 这个沉淀的价值

这个问题的价值不只是修一个 bug，而是形成了地图开发规范：

- RoadTestMap 不照搬 LogisticMap 的 GCJ02 配置。
- 覆盖物和底图必须保持同一坐标系。
- 后端坐标系和前端地图坐标系要在接口联调时明确。
- 地图类问题不能只看 DOM 和事件，也要考虑地理坐标体系。

### 4. 高精地图图层为什么要标准化

路测地图 PRD 中要求和“动态图层”保持一致。如果每个地图页面自己定义图层，就会出现：

- 同一个图层在不同页面叫法不同。
- 枚举值不同，接口或状态无法复用。
- 默认显隐规则不同，用户体验不一致。
- 后续新增图层时需要多处对齐。

因此沉淀了 HDMaps 标准图层：

- 车道边线。
- 车道中心线。
- 开阔区域。
- 路口。
- 大门。
- 停止线。

并明确哪些伪枚举不能使用，例如 `DYNAMIC_MAP`、`CENTER_MID_LINE`。

### 5. 可以写进总结的话

> 参与路测地图 BMapGL 绘制偏移问题排查。该问题表面是鼠标点击和覆盖物位置不一致，实际根因是地图底图使用 GCJ02 而覆盖物按 BD09 渲染，导致中国区域内出现约 500-800 米固定偏移。通过对比 Demo 和项目中的地图初始化、事件点位、坐标类型和覆盖物渲染方式，最终沉淀 RoadTestMap 坐标系使用规范：保持底图和覆盖物坐标系一致，默认使用 BD09，后端 GCJ02 数据在进出地图时转换。同时梳理高精地图动态图层标准，统一多个地图页面的图层枚举、文案和默认显隐规则。

## 六、远程驾驶/车辆定位重置链路 Review

### 1. 这个场景为什么需要重点审查

`rover-op-ui` 中定位重置不是普通按钮点击，而是实时指令链路：

- 用户点击后需要弹窗确认。
- 前端通过 WebSocket 发送定位重置请求。
- 请求后先收到 ack，ack 只代表指令被接收，不代表最终成功。
- 后续还要等待最终异步结果事件。
- 过程中需要心跳保活。
- 35 秒内没有最终结果，要超时失败并关闭连接。
- 关闭弹窗、重复点击、迟到结果、WebSocket 异常都可能造成状态错乱。

这类功能如果只看 UI，容易漏掉状态清理和异步竞态问题。

### 2. 具体审查什么

Code Review 关注点包括：

- 按钮可用条件是否只在车辆被接管且未 disabled 时满足。
- WebSocket 地址是否符合项目环境变量规范。
- open 后是否发送 `HEARTBEAT`，并按 5 秒间隔保活。
- 请求事件是否为 `REMOTE_REQUEST_VEHICLE_LOCATION_RESET`。
- ack 事件是否只表示继续等待，而不是直接成功。
- 最终事件 `VEHICLE_LOCATION_RESET_RESPONSE` 是否决定成功/失败。
- 35 秒超时后是否断开 WebSocket，并忽略迟到结果。
- 弹窗在确认、处理中、成功、失败之间流转是否正确。
- mock 入口是否只用于本地联调，不影响线上主流程。

### 3. 这个产出的价值

这类 Review 能体现对实时业务前端的理解：

- 前端不只是调用接口，还要管理长连接生命周期。
- 异步指令要区分“请求已接收”和“执行已完成”。
- 超时、关闭、失败、迟到消息都要有明确状态。
- mock 联调入口要和线上隔离，避免测试代码污染主流程。

### 4. 可以写进总结的话

> 参与车辆定位重置功能 Code Review。该功能通过 WebSocket 下发实时指令，存在 ack 与最终结果分离、心跳保活、35 秒超时、迟到结果忽略、弹窗状态流转和 mock 入口隔离等复杂点。我重点审查指令事件、连接清理、超时兜底、按钮可用条件和线上影响，提升了对实时指令类前端功能的工程风险识别能力。

## 七、本地联调环境和工程配置理解

### 1. 为什么这也是有价值的产出

前端实习中，能写页面是一部分，能把页面在正确环境跑起来、接到正确后端、复现线上域名行为也很重要。当前项目涉及多个测试域名和本地代理，如果不理解环境配置，会出现：

- 页面打开的不是本地代码。
- HTTPS 域名没有转发到本地 dev server。
- Host 不对导致接口或鉴权异常。
- 测试环境和本地环境行为不一致。

### 2. 具体理解和排查内容

本地 nginx 配置中，将类似 `jdxvehicle-ui-test1.jdl.cn` 的域名代理到 `http://127.0.0.1:3000`。这里需要理解：

- `server_name` 正则匹配哪些域名。
- 80 和 443 ssl 分别如何处理。
- `proxy_pass` 指向本地 dev server。
- `Host`、`X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto` 为什么要透传。
- 本地项目必须跑在对应端口，域名访问才会命中本地页面。

### 3. 可以写进总结的话

> 在本地联调过程中熟悉测试域名、nginx 反向代理、HTTPS 证书和 dev server 的协作关系，能够判断 `jdxvehicle-ui-test1.jdl.cn` 等域名是否正确转发到本地 `127.0.0.1:3000`，并基于 Host、代理配置和项目启动脚本排查页面访问及联调环境问题。

## 八、AI 辅助前端交付流程沉淀

### 1. 为什么这个产出有意义

复杂前端需求启动阶段，真正耗时的不一定是写代码，而是：

- PRD 信息量大，字段、交互、权限、页面分散。
- 接口文档可能是 PDF、Markdown、Swagger 或自然语言描述。
- 页面字段和接口字段需要逐一对应。
- 类型定义、API 方法、页面调用容易漏字段或命名不统一。
- 多项目需求需要先判断归属和缺口。

如果没有流程化工具，容易边写边猜，后期联调成本很高。

### 2. 具体沉淀了什么

近一个多月创建/使用过多个面向前端交付的流程能力：

- `pdf-parse`：解析 PDF PRD 和接口文档。
- `prd-to-tasks`：将 PRD 拆解成开发任务。
- `prd-to-page-api-mapping`：建立页面、字段、接口映射。
- `api-update-from-docs`：根据接口文档同步 API 和类型。
- `frontend-requirement-delivery`：围绕前端需求交付形成流程。

这些能力可以串成一条流程：

1. 先解析 PRD 和接口文档。
2. 拆出页面和功能模块。
3. 建立页面字段到后端接口的映射。
4. 找出现有项目中可复用的组件和接口。
5. 生成或调整类型定义和 API 方法。
6. 输出缺失接口、待确认问题和开发任务。

### 3. 具体例子：路测工具就是用这种思路拆出来的

路测工具涉及多个页面和多个项目，如果直接写代码，很容易误把监控系统、车端、运营后台的职责混在一起。通过流程化拆解后，明确了：

- 哪些页面属于 `operation-platform-ui`。
- 哪些入口或浮窗可能属于 `rover-op-ui` 或监控系统。
- 哪些车端能力还没有项目承接。
- 哪些接口和权限还需要后端确认。
- 哪些公共组件值得抽象。

### 4. 可以写进总结的话

> 探索 AI 辅助前端交付流程，将 PRD 解析、任务拆解、页面-接口映射、API/类型同步等环节沉淀为可复用工作流。以路测工具为例，先从 PRD 和接口文档中拆出页面、字段、组件、接口和跨项目职责，再识别缺失接口和权限风险，减少复杂需求启动阶段的信息遗漏和返工。

## 还能补充写入的高价值产出

下面这些不一定都要写进最终总结，但它们都具备“有价值”的特点。可以根据你想突出工程化、业务理解、复杂系统能力还是协作沉淀来选择。

### 1. 跨项目 E2E 测试方法沉淀

除了 `mobile-tools-ui` 的问题提报 E2E，当前工作区里还能看到 `operation-platform-ui` 和 `rover-op-ui` 也有 E2E 测试实践。这说明测试工程化不是单点尝试，而是可以抽象成跨项目方法。

#### 为什么有价值

运营后台和监控类项目有大量“列表 + 搜索 + 详情 + 跟进 + 状态流转”的流程。人工测试时，通常只会验证主路径，但容易漏掉：

- 搜索条件是否真的参与接口请求。
- 重置后表格是否恢复。
- 从列表进入详情再返回时，状态是否正确。
- 已结束单据是否进入只读模式。
- 列设置、筛选项等个性化配置是否持久化。
- 登录态、权限、枚举缓存、WebSocket 这类环境依赖是否会影响测试稳定性。

这些问题非常适合 E2E，因为它们本质上是用户路径和页面状态的组合。

#### 具体例子

`operation-platform-ui` 中租赁车事故管理 E2E 覆盖了：

- 按车号搜索。
- 按单据状态搜索。

### 2. 地图模块性能与架构治理思考

`operation-platform-ui/src/views/LogisticMap/docs/performanceThinking.md` 里沉淀了物流地图模块的架构思考，这块非常适合写成“复杂前端模块治理能力”。

#### 为什么有价值

地图页面通常比普通表单页复杂很多：

- 有地图底图实例。
- 有点、线、面、图层、label 等地图要素。
- 有图例开关、搜索条件、权限资源。
- 多层组件都可能需要操作地图。
- 如果地图实例和 mapApi 放得太深，就会出现 props drill、重复请求、方法层层向外抛的问题。
- 如果图例组件既管 UI 又管地图操作，会导致职责混杂。

这些问题短期不一定会造成 bug，但长期会让地图页面越来越难维护。

#### 具体治理思路

文档里提出了几个很有价值的方向：

- 按“地图底图”“地图交互”“地图要素”拆分能力，再由一个 `MapOperation` 大类统筹创建和销毁。
- 页面级别用 context 管理基础能力，例如 `baseMapRef`、图例状态、搜索条件、权限资源。
- 深层组件通过 selector 精确订阅自己需要的变量或方法，减少无意义重渲染。
- 原子化地图操作方法，业务 hook 只在需要时二次封装。
- 图例组件只负责图例 UI 和 state 更新，具体地图操作由对应图层 hook 监听状态后执行。
- 避免 `LogisticOLMap` 变成“所有地图操作都塞进去”的重组件。

#### 可以写进总结的话

> 参与/学习物流地图模块性能与架构治理思路，围绕地图底图、地图交互、地图要素三类能力拆分地图操作，思考通过页面级 context、原子化 MapOperation、局部业务 hook 和图例状态监听来降低 props drill、重复请求和深层组件耦合。这类沉淀帮助复杂地图页面从“功能堆叠”走向“可维护架构”。

### 4. 项目知识库和排障经验沉淀

`ota-ui/docs/insight.md` 中记录了很多已落地需求的关键实现结论和排障经验。这类文档虽然不是“写功能”，但对团队长期维护很有价值。

#### 为什么有价值

前端项目中很多问题不是第一次遇到，但如果没有记录，就会重复踩坑。例如：

- 上传进度为什么不能用 fetch 获取。
- 预签名 URL 返回 http 时为什么要统一替换为 https。
- 上传和表单提交为什么必须严格串联。
- React Router `<Navigate>` 为什么可能触发循环更新。
- 筛选输入态和查询提交态为什么要分离。
- React 18 StrictMode 为什么会导致开发环境初始化请求重复。

这些经验一旦沉淀下来，后续同类问题就能更快定位。

#### 具体例子

`insight.md` 中有几个适合写进总结的例子：

- 大文件上传：`fetch` 无法拿上传进度，需要 `XMLHttpRequest` + `xhr.upload.onprogress`，取消时调用 `xhr.abort()`。
- 路由权限告警：权限不足重定向时，如果目标路径重复变化或指向当前路径，可能触发 `Maximum update depth exceeded`。
- 筛选交互：列表页应区分“表单输入态”和“查询提交态”，避免输入变化就立即请求。
- StrictMode：React 18 开发模式下会额外执行 effect，网络初始化请求可能重复触发。

#### 可以写进总结的话

> 参与项目知识库和排障经验沉淀，将上传进度、预签名 URL、路由权限重定向、筛选态/提交态分离、React StrictMode 重复请求等问题记录为可复用经验，帮助团队在后续维护中减少重复排查成本。

### 6. 权限、登录态和测试环境 mock 能力

从 `operation-platform-ui` 和 `rover-op-ui` 的 E2E 可以看到，很多后台页面测试要先处理权限和登录态，否则页面会直接跳转 403 或依赖远端枚举接口失败。

#### 为什么有价值

真实后台系统里的 E2E 很少是打开页面就能测，它通常依赖：

- 登录用户信息。
- 权限资源列表。
- 枚举缓存。
- 站点/组织接口。
- WebSocket 或全局消息连接。
- 跨域请求和 OPTIONS 预检。

如果不 mock 这些环境依赖，测试会非常不稳定。

#### 具体做法

可总结为：

- 在测试启动前预置登录用户、权限资源、枚举缓存。
- 用 route mock 拦截后端接口。
- 对 OPTIONS 请求返回 CORS header。
- 用 fake WebSocket 替代真实连接。
- 只保留当前测试真正关心的业务接口。

#### 可以写进总结的话

> 在后台系统 E2E 测试中关注登录态、权限、枚举缓存、CORS 预检和 WebSocket 等环境依赖，通过 fixture、route mock、fake WebSocket 和 localStorage 预置降低测试对真实环境的耦合，使测试更稳定、更聚焦业务行为。
