# 计网八股

## 常见

### http和https的区别，用了什么机制去保证安全

1. 协议类型不同：  
  http是超文本传输协议，信息是明文传输，存在安全风险的问题。  
  https在TCP和HTTP网络层之间加入了SSL/TLS安全协议，使得报文能够加密传输。
2. 建立连接过程不同：  
  http在TCP三次握手后便可进行报文传输  
  https还需进行SSL/TLS的握手过程才可进入加密报文传输。  
3. 默认端口不同：  
  http默认端口为80  
  https默认端口号为443
4. https协议需要向CA申请数字证书，来保证服务器身份可信，一般免费的证书比较少。
5. https通过混合加密保证信息的机密性、摘要算法保证数据的完整性，将服务器的公钥放入数字证书中，进行身份验证防止冒充
    - 混合加密：非对称加密和对称加密一起使用，在通信建立前采用非对称加密的方式交换会话秘钥，通讯过程中全部使用对称加密的会话秘钥的方式加密明文数据。
    - 采用混合加密的原因： 对称加密只使用一个密钥，运算速度快，密钥必须保密，做不到安全的密钥交换。非对称加密使用两个密钥，公钥和私钥，公钥可以任意分发而私钥保密，解决了密钥交换问题但速度慢。
    - 摘要算法：为了保证数据在传输过程中不被篡改，再发送数据时我们会根据传输的内容计算出一个「指纹」，然后对方收到内容后再计算出一个「指纹」，通过比对两个指纹来判断数据是否被篡改过。  
而计算机会使用摘要算法来计算出内容的哈希值，也就是指纹，这个哈希值是唯一的，且无法通过哈希值推导出内容。
    - 数字签名对哈希值进行加密。 保证内容和哈希值不会被中间人替换，可以通过确认信息是由持有私钥的一方发出的来保证消息的来源可靠性。
    - 数字证书防止公钥是伪造的。

### 常见的http请求方法

```plain
● GET: 向服务器获取数据；
● POST：将实体提交到指定的资源，通常会造成服务器资源的修改；
● PUT：上传⽂件，更新数据；
● DELETE：删除服务器上的对象；
● HEAD：获取报⽂⾸部，与GET相⽐，不返回报⽂主体部分；
● OPTIONS：获取当前URL所⽀持的⽅法；
● CONNECT：要求在与代理服务器通信时建⽴隧道，使⽤隧道进⾏TCP通信；
● TRACE: 回显服务器收到的请求，主要⽤于测试或诊断。    
```

### 输入url会发生什么

1. url解析：  
先判断url是不是合法的URL结构，如果不是，使用浏览器的搜索引擎搜索该字符串。
2. DNS解析：

  上面的123属于迭代请求。本地服务器获得最终域名的IP地址后，会将IP地址返回给请求的用户，而用户向DNS发起请求属于递归查询。

  1. 缓存判断：判断是正确的URL后，DNS会在我们的缓存中查询有无当前域名的IP地址。若没有 就进行下一步的查询操作。  
    判断顺序：浏览器缓存->操作系统缓存->路由器缓存->ISP DNS缓存（是客户端电脑上设置的首选DNS服务器，又称本地DNS服务器。
  2. 查询IP地址：  
    客户端向本地DNS服务器发起请求后，且本地DNS服务器也并无缓存，这之后本地DNS服务器开始向各级域名服务器起迭代请求：
      1. 本地DNS服务器向根域名服务器发起请求，根域名服务器会传输回顶级域名服务器的IP地址
      2. 本地DNS服务器再向顶级域名服务器发起请求，顶级域名服务器会传输回负责的权威域名服务器的IP地址
      3. 本地DNS服务器再向权威域名服务器发起请求，权威域名服务器会传输回最终获得域名的IP地址。
    - 递归查询： 用户只需要发出一次查询请求
    - 迭代查询： 发送查询请求后，域名服务器返回单次查询的结果，下一级的查询由用户自己请求，查询方需要发出多次查询请求。
    3. 获取MAC地址：  
  当浏览器得到 IP 地址后，数据传输还需要知道⽬的主机 MAC 地址，  
  因为应⽤层下发数据给传输层，TCP 协议会指定源端⼝号和⽬的端⼝号  
  然后下发给⽹络层。⽹络层会将本机地址作为源地址，获取的 IP 地址作为⽬的地址。  
  然后将下发给数据链路层，数据链路层的发送需要加⼊通信双⽅的 MAC 地址，本机的 MAC 地址作为源 MAC 地址，⽬的 MAC 地址需要分情况处理。  
  **通过将IP地址与本机的⼦⽹掩码相与，可以判断是否与请求主机在同⼀个⼦⽹⾥，**  
  如果在同⼀个⼦⽹⾥，可以使⽤ APR 协议获取到⽬的主机的 MAC 地址，  
  如果不在⼀个⼦⽹⾥，那么请求应该转发给⽹关，由它代为转发，  
  此时同样可以通过 ARP 协议来获取⽹关的 MAC 地址，此时⽬的主机的 MAC 地址应该为⽹关的地址。
    4. TCP三次握手建立连接：_TCP协议中规定，SYN被设置为1的报文段不可以携带数据但要消耗掉一个序号_
          1. 第一次握手：客户端发送一个SYN = 1，Seq = x的数据包到服务器端口
              - SYN：请求建立连接
              - seq（sequence ： 随机序列号
          2. 第二次握手：服务器返回一个 SYN = 1，ACK = 1，seq = y， ack = x + 1，的响应包，传达确认信息
              - ACK：确认，是一个确认字符
              - ack：ack=上一次的seq+1，作用是接受上一次远端主机传来的seq，加一然后再传给客户端，提示客户端已经成功接收上一次所有数据
          3. 第三次握手：客户端再回传一个带 ACK，seq = x + 1,  ack = y + 1 的数据包，代表“握手结束”  
        确认报文段可以携带数据。但如果不携带数据则不消耗序号，在这种情况下所发送的下一个数据报文段的序号仍是x + 1  
        **然后双方就正确建立连接，开始传输数据**
    5. SSL/TLS四次握手： HTTPS协议在通信前还存在一个四次握手的过程。
          - ⾸先由客户端向服务器端发送使⽤的协议的版本号、⼀个随机数（Clien-Random和可以使⽤的加密⽅法。
          - 服务器端收到后，确认加密的⽅法，也向客户端发送⼀个随机数(Server-Random)和⾃⼰的数字证书。
          - 客户端收到后，⾸先检查数字证书是否有效，如果有效，则再⽣成⼀个随机数(Premaster secret)，并使⽤证书中的公钥对随机数加密，然后发送给服务器端，并且还会提供⼀个前⾯所有内容的 hash 值供服务器端检验。
          - 服务器端接收后，使⽤⾃⼰的私钥对数据解密，同时向客户端发送⼀个前⾯所有内容的 hash 值供客户端检验。  
    这个时候双⽅都有了三个随机数，按照之前所约定的加密⽅法，使⽤这三个随机数⽣成⼀把秘钥，以后双⽅通信前，就使⽤这个秘钥对数据进⾏加密后再传输
    6. 浏览器发送请求： 浏览器向服务器发送HTTP请求报文  
        请求报文由请求行、请求头、空行、请求体四部分组成
        - 请求行：有请求方法、请求的url、http协议及其版本
        - 请求头：把浏览器的一些基础信息告诉服务器。比如包含了浏览器所使用的操作系统、浏览器内核等信息，以及当前请求的域名信息、浏览器端的 Cookie 信息等
        - 空行：最后一个请求头之后是一个空行，发送回车符和换行符，通知服务器以下不再有请求头
        - 请求体（报文主体/请求中文）：当使用POST, PUT等方法时，通常需要客户端向服务器传递数据。这些数据就储存在请求正文中。在请求包头中有一些与请求正文相关的信息，例如: 现在的Web应用通常采用Rest架构，请求的数据格式一般为json。这时就需要设置Content-Type: application/json。
    7. 服务端响应请求并返回数据：  HTTP响应报文也是由状态行、响应头、空行、响应体四部分组成
        - 响应行/状态行：由 HTTP 版本协议字段、状态码和状态码的描述文本 3 个部分组成
        - 响应头：用于指示客户端如何处理响应体，告诉浏览器响应的类型、字符编码和字节大小等信息
        - 空行：最后一个响应头部之后是一个空行，发送回车符和换行符，通知服务器以下不再有响应头部。
        - 响应体：返回客户端所需数据  
  这个时候浏览器拿到我们服务器返回的HTML文件，可以开始解析渲染页面
    8. 页面渲染：
        1. 浏览器⾸先会根据 html ⽂件构建 DOM 树，
        2. 根据解析到的 css ⽂件构建 CSSOM 树，
        3. 如果遇到 script 标签，则判断是否含有 defer 或者 async 属性，要不然 script 的加载和执⾏会造成⻚⾯的渲染的阻塞。
        4. 当 DOM 树和 CSSOM 树建⽴好后，根据它们来构建渲染树。渲染树构建好后，会根据渲染树来进⾏布局。
        5. 布局完成后，最后使⽤浏览器的 UI 接⼝对⻚⾯进⾏绘制。这个时候整个⻚⾯就显示出来了。
    9. TCP四次挥手断开连接：
    10. 第一次挥手：TCP客户进程会发送TCP连接释放报文段，并进入终止等待1(FIN-WAIT-1)状态。
        - FIN：终止位，表示断开TCP连接
        - TCP规定终止位FIN等于1的报文段即使不携带数据，也要消耗掉一个序号
    11. 第二次挥手：TCP服务器进程收到TCP连接释放报文段后，会发送一个普通的TCP确认报文段并进入关闭等待(CLOSE-WAIT)状态。
        - 序号seq字段的值设置为v，与之前收到的TCP连接释放报文段中的确认号匹配
        - TCP客户进程收到TCP确认报文段后就进入终止等待2(FIN-WAIT-2)状态，等待TCP服务器进程发出的TCP连接释放报文段
        - 这时的TCP连接属于半关闭状态，也就是TCP客户进程已经没有数据要发送了。但如果TCP服务器进程还有数据要发送，TCP客户进程仍要接收，也就是说从TCP服务器进程到TCP客户进程这个方向的连接并未关闭，这个状态可能要持续一段时间。
    12. 第三次挥手：TCP服务器进程发送TCP连接释放报文段
        - 假定序号seq字段的值为w，这是因为在半关闭状态下，TCP服务器进程可能又发送了一些数据。
        - 确认号ack字段的值为u+1，这是对之前收到的TCP连接释放报文段的重复确认。
    13. 第四次挥手：TCP服务器进程收到确定报文段后就进入关闭状态，而TCP客户进程还要经过2MSL后才能进入关闭状态

:::info
 第一次挥手，携带断开连接的FIN=1、确定字段ACK=1、随机序列seq=u，ack=v  
 第二次挥手，携带确定字段ACK=1、随机序列seq=v，ack=u+1  
 第三次挥手，携带确定字段ACK=1、断开连接FIN=1、随机序列seq=w、ack=u+1  
 第四次挥手，携带确定字段ACK=1，随机序列seq=u+1，ack=w+1  
 等待2MSL进入关闭状态。断开连接结束通讯。

:::

### 跨域-同源策略【3.10 更新】

   跨域问题的存在主要是由于浏览器的同源策略，同源策略是浏览器的一种安全机制，为了防止一个域的脚本与另一个域的内容进行交互，保护用户免受跨站脚本和跨站请求伪造等安全威胁。

同源：协议主机端口三个都匹配，如果有任意一个不匹配就会触发跨域问题

#### 为了解决跨域问题

1. JSONP：利用标签不受同源策略的限制这一特性，采用动态插入标签来请求不同源的数据。但JSONP只支持GET请求，并且需要在服务器端进行相应的配合
    可以看出来，服务器端的配合便是要返回时使前端执行对应的回调函数。

    ```javascript
    <script>
        var script = document.createElement('script');
        script.type = 'text/javascript';

        // 传参一个回调函数名给后端，方便后端返回时执行这个在前端定义的回调函数
        script.src = 'http://www.domain2.com:8080/login?user=admin&callback=handleCallback';
        document.head.appendChild(script);

        // 回调执行函数
        function handleCallback(res) {
            alert(JSON.stringify(res));
        }
    </script>
    //后端返回如下
    handleCallback({"success": true, "user": "admin"})
    ```

2. CORS（跨域资源共享）：CORS是一种W3C规范。它定义了一种可以决定是否允许跨域请求的方式，这种方式会在浏览器和服务器端交互时被采用，所以需要浏览器和服务器同时支持。通过服务器端设置http头信息，例如Access-Control-Allow-Origin来允许跨域请求。CORS支持各种http请求，更加灵活安全

3. 代理服务器：通过搭建一个代理服务器来转发请求，使得前端可以通过代理服务器来间接访问不同源的资源。实际上是前端请求是发往同源的代理服务器，再由代理服务器请求不同源的资源

4. 使用window.postMessage：这是一个HTML5的新引入的API，允许来自不同源的脚本进行通信。通过监听window对象的message事件可以接受其他窗口发来的信息

#### 预检请求

预检请求是浏览器在发起复杂跨域请求前自动发送的 OPTIONS 请求，用来确认服务器是否允许实际的跨域操作。

它会携带 Origin、Access-Control-Request-Method、Access-Control-Request-Headers 这几个关键头信息，询问服务器是否接受当前域、请求方法和自定义头。

只有当服务器返回对应的允许头信息，浏览器才会继续发送真实的请求，否则就会拦截并抛出跨域错误。

### 浏览器中存储数据方式有哪些：

浏览器在本地计算机上存储数据，以便用户访问网站时能够更快的加载内容，提升用户体验，下面介绍四种方式：

1. cookie： 每次向同一个域名下发送请求时都会携带相同的cookie，这样服务器端就能识别客户端的身份信息。cookie是一种小型的文本文件，存储在客户端的浏览器中，主要用于身份认证、会话状态等信息。但大小会受到浏览器和服务器的限制所以只能存储少量的信息
2. localStorage：类似于电脑和手机上的下载功能，如果不主动删除可以永久保存
3. sessionStorage： 只在当前会话下有效，页面关闭时存储的数据就会被删除，可以用于临时性信息的存储。
4. IndexedDB：IndexedDB是一种浏览器本地数据库，可以在客户端浏览器中存储大量的结构化数据。它支持事务操作、索引查询等功能，存储空间相对较大，通常限制为几百MB到几GB。

### 浏览器的事件机制

主要涉及到事件的触发、传播和处理。

---

事件触发：

当用户在浏览器中进行某些操作，比如点击按钮输入文本等操作，会触发相应的事件
这些事件被封装为event对象，包含了属性和方法，供开发者在事件处理函数中使用。

事件传播：

分为三个阶段：捕获阶段、目标阶段、冒泡阶段。

在DOM2级事件模型中，事件首先在最外层的HTML元素上开始捕获，向下传递到事件的目标元素，沿途触发所有设置了捕获事件处理器的元素
接着事件处理器在事件的目标元素上执行，这是事件处理的核心机制。
最后，事件从目标元素向上回溯，触发了所有设置了冒泡事件处理器的元素，完成冒泡阶段。
这种机制允许了开发者在事件传播的不同阶段拦截并处理事件。

事件类型：

鼠标事件、键盘事件、表单事件。为开发者提供了丰富的交互能力，可以响应用户的各种操作并更新页面内容

:::warning
在事件处理过程中，浏览器还维护一个事件队列

一旦事件队列中的事件得到处理，它就会被移除。此外还支持微任务和宏任务的概念，用于管理异步执行的任务。

macro-task： script 整体代码、 setTimeout、setInterval、setImmediate、I/O、UI render

micro-task： Promise的回调、async await、process.nextTick；

:::

### 浏览器的事件循环 和 node的事件循环区别

它们都用于处理异步操作和事件驱动编程，但在实现方式和具体细节上存在一些区别：

1. 执行环境：
    1. 浏览器的事件循环在js引擎和渲染引擎之间，可能会导致线程阻塞，尤其是在渲染进程和事件循环共享同一个线程时
    2. 而Node.js中的事件循环是运行在单独的线程中，基于事件驱动模型，通过事件循环来处理和派发事件，以及执行相应的回调函数。这使得Node.js可以处理大量的并发请求。
2. 宏任务和微任务处理：
    1. 在浏览器中，宏任务和微任务是通过HTML5规范中另一的消息队列来实现的。所有的异步任务分为宏任务和微任务两种，依次加到对应的队列中，当前宏任务执行完毕后，会立即执行所有的微任务，然后再执行下一个宏任务。
    2. Node.js中，使用libuv库提供的事件循环机制来管理宏任务，并使用process.nextTick方法来实现微任务，所有宏任务分为6个不同的阶段，每个阶段会执行一些同步和异步的操作
3. 处理的事件类型：
    1. 浏览器中的事件循环主要处理用户交互事件和网络请求等异步任务
    2. Node.js的事件循环主要用于处理I/O操作和自定义的事件

流程对比：

浏览器

1. 执行scirpt代码
2. 清空微任务队列，在浏览器中只有一个微任务队列
3. 开始执行宏任务：每次出队执行一个宏任务

Node.js

1. 执行script代码
2. 清空微任务队列，Node中有nexttick队列和其他队列，清空队列优先清空nextTick队列中的任务，其中是process.nextTick中的异步任务，然后再清空其他微任务
3. 开始执行宏任务：会尝试清空当前阶段对应宏任务队列里的所有任务。

### webSocket

是HTML5提供的一种浏览器与服务器进行全双工通讯的网络技术，属于应用层协议。基于tcp传输协议，并复用http的握手通道。浏览器和服务器只需要完成一次握手，两者就可以建立持久性的连接，并进行双向数据传输。

websocket的出现解决了半双工通信的弊端。最大的特点是：服务器可以主动向客户端推送消息，客户端也可以主动向服务器推送消息。

websocket的原理：客户端向websocket服务器推送一个带有所有接收者ID的事件，服务器接收后立即通知所有活跃的客户端，只有ID在接收者ID序列中的客户端才会处理这个事件。

特点：

- 支持双向通信，实时性更强
- 可以发送文本也可以发送二进制数据
- 建立在tcp协议之上，服务器的实现比较容易
- 数据格式比较轻量，性能开销小，通信高效
- 没有同源限制，客户端可以与任意服务器通信。
- 协议标识符是ws，服务器网址是URL
- 与http协议有良好的兼容性。默认端口时80和443。握手阶段采用http协议，因此握手时不容易屏蔽，能通过各种HTTP代理服务器
- 弹幕、媒体聊天、协同编辑、基于位置的更新、直播

### SSE（Server-Sent Event）

### 【3.3】TCP/IP四层协议 OSI七层模型

#### OSI七层模型

##### OSI七层模型定义

定义： 是国际标准化组织定的一个 **网络通信分层框架**，把网络通信拆成七层，每层只管自己的事，通过接口跟上下层打通。

依次下而上是：

1. 物理层：比特流如何在物理介质传输。光纤、网线、无线电波、中继器、集线器都是物理层的内容
2. 数据链路层：将**比特流**组织成 **帧，**用MAC地址在局域网内寻址，负责差错检测。以太网、PPP协议在这层，网桥、交换机。根据MAC地址转发帧，隔离冲突域。
3. 网络层：负责**跨网络的数据传输**，用IP地址寻址，负责路由选择。IP协议、ICMP协议在这层。路由器可以根据IP地址转发包，隔离广播域做路由选择
4. 传输层：提供**端到端的通信**，管的是进程级别的通信。TCP提供可靠传输、UDP提供不可靠但快速的传输。防火墙、应用网关，能看到端口号甚至应用数据，做更精细的控制。
5. 会话层：管理**通信会话的建立、维护和终止，**NetBIOS、RPC在这层
6. 表示层：管理数据格式转换、加密解密、压缩解压。SSL/TLS的加密功能在这一层
7. 应用层：最上层 直接与用户打交道。HTTP DNS 都是应用层协议。

##### 分层的好处

1. **解耦**: 某层的改动不影响其他层，各个层之间指通过标准接口跟上下层交互
2. **标准化**： 不同厂商虽然生产出的产品不同，但都是符合OSI标准的就可以正常通信

_**实际在使用时，使用的是TCP/IP四层模型**_

##### 数据封装的过程

数据从应用层向下传输，每经过一层都会加一个头部，该过程就叫封装。
应用层产生数据 ->> 传输层会加上TCP/UDP头变成段 ->> 网络层加上IP头变成包
->> 数据链路层加上帧头帧尾变成帧 ->> 物理层把帧变成比特流发送出去
接收方反过来，把比特流一步步还原成应用数据

##### 面试官追问

#### TCP/IP四层协议

##### TCP/IP四层协议定义

是实际互联网使用的网络分层架构，把网络通信拆分成：网络接口层、网络层、传输层、应用层

从下往上：

1. 网络接口层： **在物理网络上收发数据帧**。以太网，Wi-Fi都在这层，它把网络层的IP包封装成帧，通过MAC地址在局域网寻址
2. 网络层：核心是**IP协议，负责数据包的路由和转发**通过IP地址实现跨网络的通信，路由器就工作在这一层，决定数据包走哪条路到达目的地。
3. 传输层：**提供端到端的通信服务，管的是进程之间的通信。**TCP提供可靠传输，有连接、有确认、有重传。UDP提供不可靠但快速的传输
4. 应用层：各种应用协议都在此部分，HTTP管理网页，FTP管理文件，SMTP管理邮件，DNS管理域名解析。

##### 分层好处

解耦，各层级之间互不干涉，比如说，TCP使用了新的拥塞控制算法，而其余的应用层网络层都不用修改
出问题方便排查，ping不通就是网络层问题，连接不起来是传输层问题，返回500是应用层问题。

##### 各层的数据单位和包头信息

1. 应用层： 数据单位就叫做数据，不同协议有不同的格式，HTTP有请求行、请求头、请求体。DNS有查询ID、标志位、查询记录
2. 传输层：数据单位叫报文段，TCP头部有 源端口、目的端口、序列号、确认号、窗口大小、标志位。UDP头部只有 源端口、目的端口、长度、校验和。
3. 网络层：数据单位叫数据包，IP头部有版本号、头部长度、服务类型、总长度、标识、标志、片偏移、TTL、协议、校验和、源IP、目的IP。
4. 网络接口层：数据单位叫帧。以太网帧有目的MAC、源MAC、类型、数据、FCS

##### 数据封装和解封装

应用层数据 ->> 传输层加上端口号变成报文段 ->> 网络层加上IP地址变成数据包 ->> 网络接口层加上MAC地址变成帧，最后变成比特流在物理介质上传递

解封装则是反过来的过程

物理层比特流 ->> 网络接口层拆掉帧头帧尾得到数据包 -->> 网络层拆掉IP头得到报文段 ->> 传输层拆掉TCP/UDP头得到数据。

##### 为什么说TCP/IP协议是互联网的基石

整个互联网建立在TCP/IP协议之上，IP协议让全世界的设备可以通过IP地址互相通信，TCP提供了可靠的传输，可以放心地收发数据。

#### http2.0到http3.0的升级

http3.0的传输层 由TCP 变成UDP

##### http3.0 与 http2.0的区别升级

1. 基于的传输层协议不同：
    - http2.0 使用TCP协议，
    - http3.0基于UDP协议，使用了QUIC协议，在UDP协议之上实现了自己的可靠的传输机制，解决了传输层级别的队头阻塞痛点。

2. 彻底解决了队头阻塞问题：

    - http2.0虽然将请求拆分成流，但在tcp协议级别，在前面的流没法顺利传输，就会阻塞后面的流传输。
    - http3.0之间的每个流是独立的，在弱网环境下，丢包率高，性能提升高
如何解决了队头阻塞问题：
通过QUIC传输的数据被分为一些流，流是持久性QUIC连接中短暂的子连接，每个流都处理自己的错误纠正和传递保证，但使用连接全局压缩和加密属性。所以每个http发出的请求都在自己的流上运行，丢失数据包不会影响其他流/请求的数据传输。

3. 建连速度（0-RTT）： （RTT Round-Trip Time 往返时间）

    - http2.0 需要TCP三次握手 + TLS 握手，最快也要2-3个RTT才能发送数据
    - http3.0 QUIC协议 把传输层握手和加密握手合并了，QUIC握手的过程包含了TLS，如果之前连接过，可以直接0-RTT发送数据。

4. 连接迁移：

- http2: TCP协议，靠四元组（IP：Port）识别连接，wi-fi切4G IP变了，连接就会断开，需要重连
- http3: 基于ConnectionID，ID不变，连接就一直在

#### 常见的http状态码有哪些

http状态码由三位数字组成，第一位表示类别，分为五大类

##### 1xx 信息响应

100 Continue 表示服务器收到了请求的初步部分，客户端可以继续发送请求体
101 Switching Protocols表示服务器同意切换协议，比如从HTTP升级到WebSocket

##### 2xx成功

200 OK 表示请求成功
201 Created 表示资源创建成功，POST请求创建新用户或新订单时返回这个。
204 No Content 表示请求成功但没有响应体，DELETE请求删除资源后通常会返回这个。

##### 3xx重定向

301 Move Permanently 表示资源永久重定向，浏览器会自动更新书签
302 Found 表示临时重定向，资源暂时在别的地方，下次访问还会访问原来的地址
304 Not Modified 表示资源没变过，配合缓存使用，直接使用本地缓存就行
307 临时重定向，不改变POST请求方法
308 永久重定向，不改变POST请求方法

307 308的存在对于支付、表单提交的场景下有意义，可以避免数据丢失或者重复提交

##### 4xx客户端错误

400 Bad Request 表示请求格式有问题，参数不对或者JSON格式错误
401 Unauthorized 表示没登录或者token过期，需要先登录认证【认证问题】
403 Forbidden 表示认证过了但没权限访问，普通用户访问管理员接口就返回这个【权限问题】
404 Not Found 表示资源不存在，URL错误或者资源被删了就显示这个

##### 5xx服务器错误

500 Internal Server Error 表示服务器代码抛出了异常
502 Bad Gateway 表示 网关或代理 从上游拿到了无效响应，上游服务挂了或者响应格式不对
503 Service Unavailable 表示服务暂时不可用，可能是在维护
504 Gateway Timeout 表示网关等上游响应超时，上游服务处理太慢

#### http请求中GET和POST的区别有哪些

1. 语义不同：  
 GET请求用于从服务器获取指定的资源，而POST请求则是提交或修改资源，对指定的资源进行处理。
2. 参数传递不同导致了传输数据量与安全性隐私性的不同：  
GET请求的参数暴露在url中，所以不够安全和无法保障隐私性。同时浏览器的url会有长度限制，因此导致了无法传输大量数据
POST请求的参数在请求体中，所以更加安全和隐蔽。且请求体大小没有限制，可以传输大量数据
3. 幂等性不同导致可缓存性和书签支持度不同：  
GET请求是幂等的，多次请求得到相同结果，且不会修改服务器上的资源，所以对于服务器的数据来说是安全的。因此可以被浏览器缓存，下次请求直接使用缓存数据，URL也可以被加入书签，请求参数可以被保存  
POST请求是非幂等的，多次请求会创建多个资源，所以不会缓存POST请求，也不能把POST请求保存为书签。
4. 参数类型和编码类型不同
GET只允许ASCII字符，  
POST也可以使用二进制参数  
这两者的区别也就导致了编码类型的不同，POST还可以为二进制数据多重编码。

##### 浏览器关于GET 和 POST请求的特殊处理

1. 重定向会改方法：服务器返回301、302时，浏览器会把POST方法自动改成GET方法在发送、如果POST提交表单后服务器302跳转，请求体数据就丢了。想保持POST请求需要用307状态码
2. 预检请求：跨域POST带自定义头或者JSON body时，浏览器会先发一个OPTIONS预检请求问服务器允不允许，但GET简单请求不会
3. 历史记录处理：GET请求能被收藏分享链接，POST请求后退时会弹“重新提交表单”确认框，用户体验差。

### 【3.5】HTTP和HTTPS有什么区别

#### 主要区别

1. 安全性：http的数据是明文传输，会造成安全问题，比如说被窃取会导致账号密码的泄漏等问题。而https由于在http下层加入了SSL/TLS协议，添加了加密、校验、数字证书的手段进行安全保护

<details class="lake-collapse"><summary id="u07e84f80"><span class="ne-text">加密、校验、数字证书的具体内容</span></summary><ol class="ne-ol"><li id="u1bb85fc6" data-lake-index-type="0"><span class="ne-text">加密：https通过混合加密来保证了信息的机密性。加密方式有对称加密和非对称加密，两者一起使用就是混合加密。在通信建立前采用非对称加密的方式交换会话秘钥，通讯过程中全部使用对称加密的会话秘钥的方式加密明文数据。</span></li></ol><ul class="ne-list-wrap"><ul ne-level="1" class="ne-ul"><li id="u10c7e00e" data-lake-index-type="0"><span class="ne-text">使用混合加密的原因： 对称加密只使用一个密钥，运算速度快，密钥必须保密，做不到安全的密钥交换。非对称加密使用两个密钥，公钥和私钥，公钥可以任意分发而私钥保密，解决了密钥交换问题但速度慢</span></li></ul></ul><ol start="2" class="ne-ol"><li id="u92845c8e" data-lake-index-type="0"><span class="ne-text">校验：使用了摘要算法保证了数据的完整性</span></li></ol><ul class="ne-list-wrap"><ul ne-level="1" class="ne-ul"><li id="u9dd85dbd" data-lake-index-type="0"><span class="ne-text">摘要算法：为了保证数据在传输过程中不被篡改，再发送数据时我们会根据传输的内容计算出一个「指纹」，然后对方收到内容后再计算出一个「指纹」，通过比对两个指纹来判断数据是否被篡改过。<br /></span><span class="ne-text">而计算机会使用摘要算法来计算出内容的哈希值，也就是指纹，这个哈希值是唯一的，且无法通过哈希值推导出内容。</span></li></ul></ul><ol start="3" class="ne-ol"><li id="u2b911289" data-lake-index-type="0"><span class="ne-text">数字证书：将服务器的公钥放入数字证书中，进行身份验证防止冒充</span></li></ol></details>
2. 性能：http通过三次握手就能连接成功发送数据，而https由于会在TCP握手之后多进行一次TLS握手，加密解密计算也会消耗一点CPU，但是http2的多路复用和TLS1.3的优化，导致了在实际使用时两者性能差距并不大
3. 端口：http默认80 https默认443
4. 搜索引擎：谷歌百度优先收录https，如果是http浏览器会在地址栏标红“不安全”

#### TLS协议握手

TLS的握手会根据密钥交互算法的不同，分为两种情况：

- RSA算法
- ECDHE算法【主流且具备前向安全性（即使私钥泄密，以前的消息也解不开）】

##### ECDHE算法握手流程

1. Client Hello：客户端给出随机数A，TLS版本，加密算法套件
2. Server Hello：服务端确认TLS版本是否支持，回应随机数B和确认的加密算法套件和确认的TLS版本。同时携带数字证书【内含公钥用于证明身份】，还有计算密钥需要的参数C【服务端】，并且签个名防止被改
3. Client Key Exchange： 客户端通过CA验证证书没问题，发送计算密钥需要的参数D【客户端】，并喊话，以后的数据都用密钥加密

**前三步就保证了客户端和服务端 都拥有 AB两个随机数和 CD两个计算密钥需要的参数。同时也验证了服务端的身份没有被冒充。然后各自利用算法，就可以计算出会话密钥。**

4. server Finished：服务端回应，以后的数据都会用密钥加密

1. 强制缓存[ Expires, Cache-Control ]，再次请求时就无需向服务器发送请求

##### 缓存策略，配置相关

> 根据资源类别不同 使用不同的缓存策略
>
> 1. 静态资源（css, js, 图片）：强缓存 + 内容哈希，设置较长过期时间并在文件内容变化时自动更新 URL
> 2. HTML文件：协商缓存，设置 ETag 或 Last-Modified 来验证资源新鲜度
> 3. 动态内容（接口请求的数据）：用短时效强缓存或协商缓存
> 4. 缓存分层策略，比如把高频访问的静态资源放到 CDN 上进一步优化加载速度。

### CDN【Content Delivery Network】

内容分发网络，通过地理上分布服务器网络来加速和优化网站内容传输的技术。让用户就近从最近的节点访问资源、减少跨网络、跨地域带来的限制。

工作原理：

1. 内容缓存：可以在多个地方缓存网站上的静态资源。
2. 用户请求重定向：用户发起请求的时候，优先引导到距离用户最近的、包含请求内容的边缘服务器
3. 内容传输： 边缘服务器响应用户请求，传输缓存内容给用户，减少了传输延迟和带宽消耗。

达到的效果：

1. 降低了服务器的压力：把流量分散到多个边缘服务器，减轻原始服务器的符合
2. 提升用户体验：快速加载页面和资源
3. 提高安全性：一个边缘服务器故障不影响整体的服务。

技术细节：

1. 负载均衡，分散服务器压力
2. 最优路径传输
3. 缓存策略，根据不同的内容类型和访问频率使用不同的访问策略。
